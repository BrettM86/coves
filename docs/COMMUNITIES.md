# Communities

## Accounts

Each community is its own atProto account: its own `did:plc`, its own repo, and a PDS account that this instance provisions and holds credentials for. The community repo holds the profile and the records the community issues, such as post acceptances; posts themselves live in their authors' repos (see [POSTS.md](POSTS.md)).

The profile is `at://<community DID>/social.coves.community.profile/self`. The lexicon declares its key as `literal:self`, and the community consumer rejects any other rkey on create and update. Updates to the profile are written with the community's own credentials, never the instance's.

## Handles

A community provisioned here gets the handle `c-<name>.<instance domain>`, for example `c-gardening.coves.social`. The `c-` prefix keeps community actors apart from user actors on the same PDS while staying a single-level subdomain. A community name may not start with `c-`: clients strip one leading `c-` to get the handle they display, so `c-sharp` would be shown as the handle of a community named `sharp`. Bridged communities keep their source handle with no prefix.

Clients display and link the prefix-free handle, so `LookupByHandle` retries a bare handle with `c-` when the first lookup misses. Errors other than not-found are returned without a retry, so a database outage never looks like a missing community.

`!name@instance` is a display form that clients build from `name` and the instance. No record stores it, but the API accepts it as input. `ResolveCommunityIdentifier` takes a DID, a handle (with or without `c-` or a leading `@`), `name@origin` with or without `!`, or a bare name on this instance. A local origin rebuilds the `c-` handle. A remote origin resolves against the `(name, origin)` pair the consumer stored at ingest, which lets a bridged community be addressed by the instance it came from rather than by its DNS handle. Which handles a community DID may claim, and the `hostedBy` did:web check, are in [SECURITY_MODEL.md](SECURITY_MODEL.md).

## Credentials

The community's PDS password, access token and refresh token are sealed with AES-256-GCM before they reach Postgres ([CREDENTIAL_ENCRYPTION.md](CREDENTIAL_ENCRYPTION.md)). The password is encrypted rather than hashed because the session fallback below sends it in clear. Credential fields carry `json:"-"`.

`EnsureFreshToken` runs before every write to a community repo. It locks a mutex for that community DID, re-reads the row in case another goroutine already refreshed, and refreshes when the access token expires within 5 minutes. If the refresh fails with an expired-token error, it falls back to `createSession` with the stored email and password; any other refresh error is returned. Refresh tokens are single-use, so the new pair is written at once with three attempts. If all three fail, the call errors and the stored refresh token is already spent. The mutex lives in one process and does not serialize refreshes across several AppView instances.

Raw PDS calls made by `callPDSWithAuth` time out after 10 seconds for reads and 30 seconds for `createAccount`, `createRecord` and `putRecord`. Writes got the longer limit because community creation failed at 10 seconds on slow PDS writes (keypair generation and PLC registration). Indigo XRPC calls in the package, including token refresh, run under a 30-second ceiling that covers their retries.

## Hosted communities

A community is hosted by this instance when `pds_refresh_token_encrypted IS NOT NULL`, meaning the AppView holds credentials that can sign for it. `hosted_by_did` is never used for this, because it comes from a record anyone can write. The query is `NewHostedCommunityQuery` in `internal/db/postgres/community_hosted.go`, and the Discover hosted bonus uses the same predicate.

## Subscriptions

A subscription is a `social.coves.community.subscription` record in the user's repo whose `subject` is the community DID. The consumer indexes creates, updates and deletes by record URI, so an update that changes the subject moves the row to the new community. Subscribing when the viewer's PDS already holds a record for the community rewrites that record with putRecord rather than creating another. `contentVisibility` runs from 1 (only the best content) to 5 (all content), is clamped to that range, and defaults to 3. Only the home timeline reads it: levels 1 and 2 keep a community's posts at or above its top-10% / top-25% score line over its visible posts from the last 14 days (score above 0 only), levels 4 and 5 boost the Hot rank by 1.5× / 2×, and level 3 is the unchanged feed. Discover and community feeds ignore it. The optional boolean `favorite` marks a community the subscriber has pinned; it defaults to false, and `viewer.favorite` reports it on community views only when the viewer is subscribed. When the viewer already has a record, a subscribe call that supplies `contentVisibility` or `favorite` rewrites that record and carries the other setting over as the index reads it; one that supplies neither writes nothing. The rewrite passes the listed record's CID as `swapRecord`; if another writer changed the record first, the service re-lists and rewrites the same record (same rkey) from its fresh contents, up to 3 attempts, then answers 409 `SubscriptionConflict`. It also answers 409 without writing when the re-list finds the record deleted or replaced by a different record. The response always carries `favorite` and `contentVisibility` as stored after the call.

`subscriberCount` comes only from indexed subscription rows. A trigger added in migration 045 maintains `communities.subscriber_count`, and the profile record cannot set it. Go code must not adjust the count itself: a binary that still did would double-count against the trigger, which is why the migration header warns against overlapping old and new binaries in a rolling deploy.

## Blocks

A `social.coves.community.block` record in the user's repo hides that community from the viewer's aggregate feeds only. The exact surfaces are in [FEEDS.md](FEEDS.md).

## Creation

`COMMUNITY_CREATION` decides who may call `community.create`: `anyone` lets any signed-in account create a community, and `instance-admins` limits it to the instance admins in `MODERATION_ADMINS`. Unset or empty means `instance-admins`, and any other value fails config validation at startup. Under `instance-admins` a caller who is not an admin gets 403 `CommunityCreationRestricted` before the AppView contacts the PDS. The setting gates creation only: ownership transfer and admin owner assignment do not read it. Production sets it explicitly in `/opt/coves/.env`; the CI and dev env files set `anyone`. `community.suggestion.updateStatus` is limited to the same `MODERATION_ADMINS` list (it used to read the old `COMMUNITY_CREATORS` list). The handler rejects a client-supplied `createdByDid` or `hostedByDid`; the service derives both from the session and the instance configuration. When `PDS_ADMIN_PASSWORD` is set, the AppView mints a single-use invite before creating the community's PDS account, so creation works on an invite-required PDS.

After the profile record, `community.create` writes the creator's `owner` record (`social.coves.community.moderator` at `RoleRecordKey(creator)`) as the community, then indexes it into `community_roles` once the community row is stored, so the creator can change the community before the firehose copy arrives. A failed owner-record write fails the create. A retry by the same creator resumes the interrupted account and writes the profile and the owner record with `putRecord`, so a record the interrupted create already wrote does not fail it. A failed local index write is logged and left to the firehose.

## Community moderators

A community's owner and moderators are `social.coves.community.moderator` records (held back, unpublished; see [LEXICON_PUBLISHING.md](LEXICON_PUBLISHING.md)) in the community's own repo, not the moderator's, so the community PDS revokes a role at once by deleting the record and another instance cannot forge or keep one. A record carries `subject` (DID), `role` (`owner` or `moderator`, an open set up to 64 bytes) and `createdAt`. Its record key is the subject's derived key, the same unpadded lowercase base32 SHA-256 of the subject DID as a ban record (`communities.RoleRecordKey`), so a community holds one role record per account.

The communities consumer indexes the records into `community_roles`, one row per (community, subject), rev-gated by record URI so a stale create replayed after its delete does not bring a role back. A record in a repo that is not an indexed community is refused as an unresolved reference and redriven; a record at any other key, or with an invalid subject, role or `createdAt`, is refused permanently. An unknown `role` is stored as written and grants nothing. There is no cap on moderators. `community_memberships.is_moderator` is unused.

Owner rule (`communities.EffectiveRoster`): among `owner` records the one with the latest `createdAt` is the owner, with ties going to the lexically greatest record key; every other `owner` record reads as `moderator`. The rule does not depend on delivery order, so every indexer reading the same records agrees.

Two public queries read the index: `social.coves.community.getModerators?community=` (any identifier `community.get` accepts) returns the owner and every moderator, and `social.coves.community.getActorRoles?actor=` returns the communities an account holds a role in, with its effective role in each.

A role applies only in a community this instance hosts (PRD § 3). Role records are indexed from every indexed community, but both queries serve roles only in hosted communities, by the predicate in [Hosted communities](#hosted-communities). `getModerators` for a community this instance does not host returns an empty roster: no owner and no moderators, not an error. `getActorRoles` omits such communities. Deleting a community deletes its `community_roles` rows in the same transaction.

### Owner authority

`communities.RoleAuthorizer` (`NewRoleAuthorizer` in `internal/core/communities/role_authorizer.go`) answers whether an account may act as owner or moderator in a community, and every community endpoint that needs a role uses it. The community must be hosted (the predicate above, never `hosted_by_did`) and not removed by this instance; a removed community is refused with `CommunityRemoved`, anything else with `Forbidden`. The role comes only from the effective roster of the index; an owner satisfies a moderator requirement. `community.update` requires the owner. The profile's `createdBy` is kept as history and grants nothing: a creator whose owner record was replaced cannot update the community.

An in-force instance account ban, or a stored `takendown` or `suspended` PDS account-status restriction ([MODERATION.md](MODERATION.md)), suspends the holder's roles. Nothing is rewritten: the record and the `community_roles` row stay, and the role works again once the ban lapses or is lifted, or the restriction is cleared. A failed read of any of these is an error, never a refusal.

An instance admin (`MODERATION_ADMINS`) may take owner and moderator actions in any hosted, not-removed community, reported as an admin acting for the community. An admin who also holds a satisfying role acts by that role. Admin status is not a role: `community.get` and `getViewerAuthority` do not report it as one.

`community.get` carries `viewer.role` (`owner` or `moderator`) for a signed-in viewer with a usable role; it is absent otherwise. `actor.getViewerAuthority` carries `hasCommunityRole`, whether the viewer holds a usable role in any hosted, not-removed community.

Moderators read a subject's community moderation state and version with `social.coves.moderation.getCommunityState`; see [MODERATION.md § Community moderation: state and versions](MODERATION.md#community-moderation-state-and-versions).

### Resign and remove

`social.coves.community.resignModerator` (`community`, `expectedVersion`, `idempotencyKey`) lets a moderator give up its own role. `social.coves.community.removeModerator` (`community`, `subject`, `expectedVersion`, `idempotencyKey`) lets the owner, or an instance admin, remove a moderator; an admin's removal is logged as an admin acting for the community. Both are authenticated procedures served by `internal/api/handlers/moderation/community_roster.go` over `moderation.CommunityActionService`, and both return `community`, `subject` and the roster `version` after the change. `expectedVersion` is the roster version from `getCommunityState` with the community's DID as subject; a stale one is `StateConflict`. The same key with the same request returns the first result; with a different request it is `IdempotencyConflict`.

Each deletes the subject's role record from the community's repo with the community's credentials, under the repo head it read (`swapCommit`), and drops the `community_roles` row in the same request, so the removed account's authority ends when the response returns. A request by the removed moderator that was already authorized but had not yet taken its locks is refused when it rechecks authorization under them. The owner cannot resign (`OwnerMustTransfer`; it must transfer ownership first, § Invitations and ownership transfer) and the owner's record cannot be removed (`CannotRemoveOwner`). A subject with no moderator role, or whose record is already gone from the repo, is `RoleNotFound`. A caller who is not a moderator (resign) or the owner or an admin (remove), and any community that is not hosted or is removed, gets `Forbidden`. The write pipeline, its locks and its recovery after a lost PDS response are in [MODERATION.md § Community moderation: actions](MODERATION.md#community-moderation-actions).

Every role change is one action in `moderation_actions`: `remove-role` for a resignation or removal, naming the actor, and `grant-role` for the creator's owner record at community creation, naming the creator. A role record created, rewritten or deleted outside this instance, in any indexed community, gets one action with no actor.

### Invitations and ownership transfer

Nobody is made a moderator or owner without accepting (PRD Q2). An invitation is AppView state in `community_role_invitations` (migration 085), not a record: inviting, declining and a lapse write nothing to the community's repo, log no moderation action and leave the roster version unchanged. The invitee is not on the roster until it accepts. The endpoints are authenticated procedures and queries served by `internal/api/handlers/moderation/community_invitations.go` over `moderation.CommunityInvitationService` (invite, offer, decline, lists) and `moderation.CommunityActionService.AcceptInvitation`.

- `social.coves.community.inviteModerator` (`community`, `subject`, `expectedVersion`, `idempotencyKey`): the owner, or an instance admin, invites an account to moderate. `subject` is a handle or a DID; a handle is resolved through the instance's configured identity resolution, and one that does not resolve is `AccountNotFound`. An invitee that already holds any role is `InviteeHasRole`.
- `social.coves.community.offerOwnership` (same input): the owner offers ownership to one of the community's current moderators (anyone else is `InviteeNotModerator`); an instance admin may offer it to any account. Offering it to the current owner is `InviteeHasRole`.
- Both return the `invitation` (`community.defs#invitationView`: `id`, `community`, `subject`, `role`, `inviter`, `createdAt`, `expiresAt`) and the roster `version`. A moderator or an unrelated account is `Forbidden`, as is any community that is not hosted or is removed.
- `social.coves.community.acceptInvitation` (`invitation`, `expectedVersion`, `idempotencyKey`) returns `community`, `subject` and the roster `version` after the change. `social.coves.community.declineInvitation` (same input) returns the `invitation` ID. Only the invitee may accept or decline; for anyone else, and for an unknown ID, the answer is `InvitationNotFound`, so the endpoints do not reveal that an invitation exists.
- `expectedVersion` is the roster version, checked under the roster lock (`StateConflict` when stale), and each request has the idempotency rules of § Resign and remove.

There is at most one open invitation per (community, invitee). A newer invitation or offer to the same account in the same community replaces the open one (`superseded`); accepting or declining a replaced, declined or accepted invitation is `InvitationNotOpen`. So an admin's ownership offer to an account replaces that account's open moderator invitation.

An invitation lapses 14 days after it was made (`communities.InvitationLifetime`). The lapse is computed when read; nothing sweeps or rewrites the row. A lapsed invitation is not served as pending, accepting or declining it is `InvitationLapsed`, and it does not block a new invitation.

An account with a community ban in force in the community cannot be invited or offered ownership, and cannot accept while the ban is in force: both are `InviteeBanned`. The ban is read under the invitee's ban-subject lock, so a ban indexed concurrently is either seen or waits for the request. A lapsed ban does not count.

Accepting runs the roster write pipeline of § Resign and remove: the rules are checked again under the locks, the community's repo is written under the head it read, and the index, the roster version, one moderation action and the invitation's `accepted` state change in one transaction before the response returns. At acceptance:

- a moderator invitation whose invitee now holds any role, or an admin's offer whose invitee is now the owner, is `InviteeHasRole`;
- an owner's offer whose invitee is no longer a moderator is `InviteeNotModerator`;
- an owner's offer whose inviter is no longer the effective owner is `InvitationStale`.

A moderator invitation creates the invitee's `moderator` record at `RoleRecordKey(invitee)` and logs `grant-role`. An ownership offer is a transfer: one `applyWrites` call writes the new owner's `owner` record and rewrites the previous owner's record as `moderator`, and logs one `transfer-ownership` action. Both index rows change in the same transaction, so local authorization never sees zero or two owners. The action's actor is the inviter (an admin's is logged as an admin acting for the community), with the invitee as subject; the idempotency record belongs to the invitee. A lost PDS response is recovered by retry, the intent sweep or the firehose copy of the write, as for removals.

Admin recovery of an ownerless community: an instance admin offers ownership to any account with `offerOwnership`. Accepting writes only the new owner's record, since there is no previous owner to demote.

Privacy: invitations are seen only by the community's owner, instance admins and the invitee. `social.coves.community.listInvitations?community=` serves a community's pending invitations to its owner or an instance admin; moderators and everyone else get `Forbidden`. `social.coves.community.listViewerInvitations` serves the caller's own pending invitations across communities, each with the community's current `rosterVersion` (the invitee cannot read `getCommunityState`, so this is where it gets `expectedVersion`); no parameter names another account. `community.get` carries `viewer.invitation` (`id`, `role`, `expiresAt`) for the invitee's pending invitation only. `getModerators` and `getActorRoles` never list an invitee. The invitee gets a `communityInvitation` notification ([NOTIFICATIONS.md § Reasons](NOTIFICATIONS.md#reasons)). Deleting a community deletes its invitations in the same transaction.

### Account erasure

Erasing an account (`social.coves.actor.deleteAccount`, `user_repo.go` `Delete`) removes it from every roster in the erasure transaction: first every `community_role_invitations` row naming it as invitee or inviter, in any state, then every `community_roles` row for it. Each community that lost a role row, hosted or not, advances its roster version once. Any failure rolls the whole erasure back.

The role records stay in the community repos until they are deleted there. For each removed row in a hosted community, erasure queues a delete in `community_role_record_deletes` (migration 086): community DID, record key and the row's CID. The erased DID is not stored; the record key is its hash (`RoleRecordKey`). `moderation.RoleRecordDeleteQueue` deletes each record with the community's credentials, guarded on that CID (`swapRecord`). `cmd/server` sweeps the queue every 2 minutes and starts one sweep right after each erasure commits. A delete that succeeds, finds the record already gone, conflicts on the CID, or finds the community no longer hosted is finished, and its row is deleted, so the queue keeps no record keys of erased accounts. Any other failure keeps the row with a failure code (`credentials_failed`, `pds_delete_failed`, `pds_timed_out`) and retries it 1 minute later, doubling per failure up to 1 hour. Deleting a community deletes its queue rows. The firehose copy of a queued delete changes nothing, since the row is already gone.

A record naming an erased account is never indexed afterwards. The role consumer, every write completion (the request itself, a retry, the intent sweep or the firehose copy) and the creator's owner record at community creation take the subject's shared erasure gate before they write: an erased subject gets no `community_roles` row and no version change, and in a hosted community the written record's delete is queued at its CID. An intent whose subject was erased before it completed ends `failed`. Because a returning account (`ReinstateAccount`) loses its erasure marker, erasure also marks each record of an open create or update intent naming the account (`community_write_intent_erasures`, migration 086: intent ID and whether it is a transfer's paired record, no DID), and every completion treats that record's subject as erased: a write whose response was lost before the erasure never gives the returning account its role back, and its committed record's delete is queued instead. Deleting a community deletes these marks with its intents. `inviteModerator` and `offerOwnership` with an erased inviter or invitee write nothing and return `AccountNotFound`.

Known gap: `community.create` writes the creator's owner record to the community repo with no intent, then indexes it locally (a failure there is only logged) or through the firehose copy. If the creator is erased after the repo write and before either indexes the record, erasure finds no role row and no intent to mark, and queues no delete. If the account then signs up again (`ReinstateAccount`) before the record is indexed, no erasure marker stands, the old owner record is indexed, and the returning account is the owner again. Nothing deletes that record. Recovery is an instance admin transferring ownership with `offerOwnership`, which demotes the returning account to moderator, then removing it with `removeModerator`.

When the owner is erased the community is ownerless. Moderators keep their roles and moderator actions. Owner actions (`community.update`, `inviteModerator`, `offerOwnership`, `removeModerator`) are `Forbidden` to everyone but an instance admin, who restores an owner with `offerOwnership` (§ Invitations and ownership transfer).

Re-signup before the sweep: an account erased and then signed up again (`ReinstateAccount`) can find its old record still in a community repo, unindexed, with its delete queued. Accepting a new invitation there rewrites the record at the account's key (an update, under the repo head it read) instead of refusing it, but only when the queued delete carries exactly the CID of the record in the repo; any other unindexed record at the key is `StateConflict`. The queued delete then conflicts on the new CID and its row is deleted, and the new record stays indexed.

### Runbook: back-filling owner records

Communities created before `community.create` wrote an owner record have no owner, so only instance admins can change them. `cmd/backfill-community-owners` writes one. Run it once, in the same deploy, right after the new AppView has started (so its consumer indexes the records it writes), with the AppView's environment (`DATABASE_URL`, `ENCRYPTION_KEY`, `IS_DEV_ENV`, and the rest `config.Load` reads):

```
go run ./cmd/backfill-community-owners [-timeout 1h]
```

For each hosted community it lists the repo's role records on the PDS (not the index); a repo that already holds an indexable `owner` record (a `did:plc` or `did:web` subject at `RoleRecordKey(subject)`, the rule the indexer applies) is left alone, so a rerun writes nothing. A repo whose `owner` records all fail that rule gets no write and is counted as `owner-unindexable`; the log names the community DID and the record URI, and an instance admin must assign that community an owner. A listRecords cursor that repeats fails the community rather than risk writing a second owner over one on an unread page. Otherwise it writes an `owner` record for the profile's `createdBy` at `RoleRecordKey(createdBy)`, signed in with the community's stored handle and password. It writes no database rows, not even refreshed tokens. A community is skipped when `createdBy` is empty, is not an indexed account, or is an erased account; a console-created community whose `createdBy` is an indexed admin account gets that account as owner. It prints `written`, `already-owned`, `owner-unindexable`, `skipped` and `failed` counts. A failing community is logged and the run continues, and the command exits non-zero if any failed; rerun it after fixing the cause. A skipped or owner-unindexable community has no owner until an instance admin acts for it.
