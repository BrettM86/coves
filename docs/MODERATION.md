# Moderation

Formerly `docs/PRD_ADMIN_MODERATION.md`. Code comments cite this file by section heading and by decision ID (Q-I6, Q-ORACLE, D-QUOTES), so keep both stable.

Server admins remove and restore posts and comments, apply or retract an NSFW label on posts, ban or unban accounts, and remove or restore communities. The service is `internal/core/moderation`, the state is in migrations 050 to 052 (community comment removals in 067, published labels in 071, account and community subjects in 072 and their recorded kind in 075, account-ban hide markers in 073, PDS account-status restrictions and their rechecks in 074 and 076, and community record writes in 080), and the served endpoints are `social.coves.moderation.removeContent`, `restoreContent`, `labelContent`, `retractContentLabel`, `banAccount`, `unbanAccount`, `removeCommunity`, `restoreCommunity`, `getSubjectState`, `listActions` and `listAdminActions`. The other schemas in that lexicon directory have no routes: `ban` is the community ban record that Coves moderators (through `social.coves.community.banAccount` and `unbanAccount`) and Tidepool write and the consumers index ([POSTS.md](POSTS.md) § 4.1), and `ruleProposal`, `tribunalVote` and `vote` are held back. The unrouted `banUser`, `unbanUser`, `listBans` and `getBanStatus` were deleted, replaced by `social.coves.community.banAccount`, `unbanAccount` and `listBans`.

## Scope

A removal redacts content from this instance's served views. It never writes to the author's PDS and never rewrites author self-labels.

In a community hosted on this instance (the AppView stores its PDS credentials; `hosted_by_did` is not consulted), an applied removal of a post or comment also writes the community's own removal record, in one commit that deletes a standing acceptance. The record carries the reviewed strongRef, a public code (spam stays `spam`; rule violation and harassment become `rule-violation`; doxing, illegal content and moderator discretion become `moderator-discretion`) and the action's time, and never the reason or private note. Restoring that removal deletes the record and, if the removal withdrew an acceptance, writes one pinning the post's CID indexed at restore. A post that was never accepted returns to pending, and a post its author deleted gets no acceptance. A removal record the instance did not write is never rewritten or deleted. The write is a durable outbox row recorded in the moderation transaction (migration 080, `moderation_community_record_writes`), attempted after commit and retried by a sweep every two minutes. In a community hosted elsewhere, a removal writes no community records; community admission stays a separate constraint on visibility.

Tidepool does not consume the removal records written in hosted communities; it still follows instance removals through signed `!takedown` labels (§ Published labels). With `COVES_LABELER_DID` set, Tidepool follows `com.atproto.label.subscribeLabels`, sends a `Delete` for native content it delivered and an `Undo{Delete}` on negation, and withholds bridged content (Tidepool docs/PROTOCOL.md, "Coves instance takedowns"). Without that consumer, copies already delivered to Lemmy stay there.

Content state is several independent facts, never one `deleted` flag: the author's record lifecycle, community admission, active moderation decisions (each with its own authority and scope), and active classifications such as NSFW. An author edit, a firehose replay, a delete and recreate at the same URI, or community re-acceptance does not clear a standing removal. Decisions are keyed by subject URI; a different URI is a different subject.

## Authority

Admins are the DIDs listed in `MODERATION_ADMINS`. An empty list grants nobody, and config validation rejects an entry that is not a DID. `RequireInstanceAdmin` in `internal/api/middleware/admin_auth.go` checks the caller's DID (OAuth session or PDS service JWT) against the list before any handler or idempotency replay runs. Never authorize by handle, community creatorship, PDS ownership or a caller-supplied actor field. The authority DID on every action is `SERVER_DID`.

Any admin may reverse another admin's decision within the same authority and scope, and history keeps both actors. Removing a DID from the list does not erase or retract its past actions.

The list is read at boot. To change it in production, edit `MODERATION_ADMINS` in `/opt/coves/.env` and recreate the AppView (`docker compose -f docker-compose.prod.yml up -d --no-deps appview`, see `docs/PRODUCTION_DEPLOY.md`).

Keep `MODERATION_ADMINS` empty until supported web and mobile builds pass release gate 5 in [LEXICON_PUBLISHING.md](LEXICON_PUBLISHING.md). There is no `#notFoundPost` fallback: `post.get` serves `#moderatedPost` for every instance removal, so a client that cannot decode it breaks as soon as an admin acts.

## What the viewer may do

Clients never probe admin endpoints to learn whether to show moderation controls. Post, comment and `#moderatedPost` views carry `viewer.moderation`, the action tokens the signed-in viewer may take, using the modlog's action names. For an instance admin, a live post gets `remove` and `label`, or `remove` and `retract-label` when this instance's NSFW label is active. A live comment gets `remove`. Content this instance removed gets `restore`, including a comment its author also deleted. Signed-out viewers, non-admins, content only another authority removed, and author-deleted comments this instance did not remove get no field. `PostViewerActions` and `CommentViewerActions` in `internal/core/moderation` compute the lists.

Screens with no item call `social.coves.actor.getViewerAuthority`, which needs authentication and returns `{instanceAdmin}` from `MODERATION_ADMINS`, `false` for a non-admin rather than `Forbidden`. It also returns `hasCommunityRole`, whether the viewer holds a usable owner or moderator role in a community this instance hosts and has not removed, and `community.get` carries the viewer's role there as `viewer.role` (`owner` or `moderator`, absent otherwise; see [COMMUNITIES.md](COMMUNITIES.md) § Community moderators). Admin status is not a role.

Community authority has its own list, `viewer.communityModeration`, served beside `viewer.moderation` on post views, `#moderatedPost`, `#removedPost`, comment views and `community.get`. It is computed for any signed-in viewer from that viewer's authority in the item's community, decided by the community role authorizer: the owner, or an instance admin acting for the community, has owner authority; a usable moderator has moderator authority; anyone else, including a moderator under an instance account ban, gets no field. An admin who also moderates the community gets both lists. The tokens are an open set:

- Posts: `remove` when the community's admission status is accepted, pending or pending reacceptance; `restore` when the community removed it; neither for a rejected post or one with no admission row. `ban-author` follows whatever the admission status unless the author holds a role in the community, which a community ban refuses. `#moderatedPost` uses the post's community admission status from the raw row. `#removedPost` gets `viewer.communityModeration` of `restore` only: the tombstone carries no author, so a ban-author control is not actionable from it, and serving the author to moderators would widen what it discloses.
- Comments: `remove`, or `restore` when a removal source is the comment's own community; then `ban-author` unless the author holds a role. A comment its author deleted gets nothing. The comment's community is the one its parent chain reaches.
- Communities (`community.get`): moderators get `ban-account` and `unban-account`; owner authority adds `grant-role`, `remove-role` and `transfer-ownership`. `ban-author`, `ban-account` and `unban-account` have no modlog name, because a community ban logs as removing and restoring an account.

`CommunityPostViewerActions`, `CommunityCommentViewerActions`, `CommunityViewerActions` and `NewCommunityViewer` in `internal/core/moderation` compute the lists. Handlers read each community's authority, and each (community, author) role, once per request. A failed read omits that community's lists and logs at ERROR; the procedures still authorize every action.

## Served shapes

- A removed post's thread (`getComments`) returns `NotFound`. Its comments stay in their authors' repos and come back when the post is restored.
- `post.get` returns `#moderatedPost` for a removed post: no record, title or embed. It goes only to a viewer who could have seen the post had it not been removed (`AdmittedURIsForViewer`), so a removal never discloses a pending or rejected post. `#removedPost` keeps its meaning of a community removal and is never substituted.
- Feeds, search, Discover and profile activity exclude removed posts. Profile activity also drops removed comments and every comment whose root post is removed.
- A removed comment reuses the author-deleted placeholder: `record` absent, `isDeleted`, `deletionReason: moderator`, a `moderation` object naming the source authority and scope, author handle `handle.invalid`, zero vote stats, and thread references and `replyCount` kept. Its replies stay in the thread. If the author also deleted it, `deletionReason` stays `author` and the `moderation` object is still attached.
- `commentView.record` is optional under an approved output-loosening exception listed in LEXICON_PUBLISHING.md. The wire shape did not change; the AppView had always served deleted comments without a record. `handle.invalid` replaced an empty string that failed `format: handle`.
- `blockedComment.blockedBy: moderator` is published but never emitted.

D-QUOTES: Coves-quoted posts are not hydrated server-side. The served quote is a strongRef only, so a removed quoted post leaves no copied content to redact, and `post.get` on its URI returns `#moderatedPost`.

## Removal and NSFW

Removal and NSFW are independent decisions. Removal always wins: a reveal control never shows removed content, applying or retracting NSFW never restores a removal, and restoring never clears NSFW. NSFW is posts only and URI-scoped, so an edit does not drop it. It appears in `postView.moderation.contentLabels` next to the verbatim record and never changes feed eligibility, search or ranking. Clients combine it with the author's self-labels to drive their existing blur.

## Reasons

Reasons are the tokens in `moderation.defs`: spam, harassment, doxing, illegal-content, rule-violation and moderator-discretion. A seventh, subject-moved, is written only by Coves on the system actions described under [Community comment removals](#community-comment-removals). No request accepts it, and it appears only in action views (`actionReasonType`), not in `reasonType`. There is no public free text; private notes are admin-only. A `csam` report reason exists only in `adminreports`; an admin picks illegal-content when acting on one.

A removal's reason cannot be corrected out of the public log. Hiding is decided per entry, from its own reason and its reversed action's reason, and there is no amend API, so a restore and re-removal leaves the first entries public. Choose doxing or illegal-content on the first removal.

Doxing and illegal-content are remove-only. Q-RESTORE-REASON (2026-09-29): `restoreContent` rejects them with `UnsupportedReason`. Q-LABEL-REASON (2026-09-30): `labelContent` and `retractContentLabel` reject them the same way.

Public modlog entries whose reason, or whose reversed action's reason, is doxing or illegal-content omit the subject URI, CID and community, and are left out of any query filtered by subject, collection or community. The record is still fetchable from its author's PDS, and the log must not link to it. Q-ORACLE, accepted 2026-09-29: someone who already holds a URI can see that it is removed, find no public entry naming it, and infer the reason was doxing or illegal content.

## Errors

The vocabulary is the sentinel list in `internal/core/moderation/errors.go`: AuthRequired, Forbidden, InvalidRequest, InvalidSubject, SubjectNotFound, DecisionNotFound, InvalidDecision, ContentChanged, StateConflict, IdempotencyConflict, UnsupportedReason, UnsupportedLabel, InvalidCursor and ModerationUnavailable. `tests/lexicon_moderation_test.go` pins the seven content and modlog endpoints to the subset each can return; the account and community endpoints are not in that test. `ErrSubjectNotIndexed` and `ErrResolverUnavailable` never reach the wire alone.

Authorization runs before any subject or decision lookup. InvalidDecision (a reversal aimed at the wrong action kind, at another authority or scope, or at a decision no longer active) mutates nothing. A stale `expectedVersion` is StateConflict; a reviewed CID that no longer matches the indexed record is ContentChanged. An unindexed but well-formed URI has a state from `getSubjectState` (version `v0`, record unavailable), while `removeContent` and `labelContent` return SubjectNotFound for it.

## Account bans

`banAccount` and `unbanAccount` take an account DID (`subject`), `expectedVersion`, `idempotencyKey`, `reason` and an optional `privateNote`; `banAccount` also takes an optional `expiresAt`. Both are behind `RequireInstanceAdmin`, so a signed-out caller gets AuthRequired and a non-admin Forbidden. The moderation subject of an account is `at://<did>` with no collection (migration 072), and its version is read and checked through `getSubjectState` like any other subject. A subject that is not a DID is InvalidRequest. `banAccount` on a DID that is an indexed community is InvalidSubject unless the DID also has account activity (an account `users` row or an authored post, comment or vote) and its community row is not a trusted bridge's community (stored `pds_url` a trusted bridge host and stored `handle` under that host's registrable domain); such a DID (one that indexed as a community before its account footprint) is banned as an account, an account-kind decision that hides its authored content and refuses its writes like any ban. Other communities, including trusted-bridge ones, are moderated with `removeCommunity`. The check reads these facts, including whether the DID has a `communities` row, under the subject lock and comes before the version check; nothing read before the lock decides it. `unbanAccount` lifts an active ban even when the DID has since been indexed as a community; with no active ban, an indexed community's DID is InvalidSubject. Doxing and illegal-content are accepted on a ban and refused on an unban with UnsupportedReason, as for restore. `restoreContent` given the action ID of an account ban or a community removal is InvalidRequest; `unbanAccount` and `restoreCommunity` reverse those.

A ban is one `remove` action on `at://<did>` and the instance removal decision on that subject, with a `!takedown` label on the bare DID. `expiresAt` makes it temporary. It must be strictly after the server's clock, or the call is InvalidRequest; it is stored at millisecond precision (truncated, UTC) and is part of the idempotency request, so the same key with a different expiry is IdempotencyConflict. The replay check runs before the expiry check, so replaying a ban after its expiry returns the original result. A ban is in force while its decision is active and `expiresAt` is absent or later than the server's clock (`accountbans.Ban.InForce`). At `expiresAt` it ends with nothing written: no job, action, label or modlog entry, since the label's `exp` already tells consumers it no longer applies.

`banAccount` with the current version on an account whose ban is in force replaces it with a new action, carrying the new expiry or none, and writes a new `!takedown` whose later `cts` supersedes the old one. On a lapsed ban it is a new ban. On a DID whose active decision is a community removal (a removed community whose row was deleted) it is StateConflict. `unbanAccount` on an active ban, in force or lapsed, records a `restore` that reverses it, deactivates the decision and writes the `neg`. With no active ban it is StateConflict.

While a ban is in force, the account's posts (every author class, aggregators included), comments and votes are refused with `Banned` ("Your account is banned on this instance") before any PDS write or ledger reservation; after an unban or after `expiresAt` they are accepted. A post that reaches the acceptance engine while its author's ban is in force (a firehose post, or an accepted post edited and awaiting re-acceptance) is neither rejected nor removed: the engine defers it, and decides it normally on a pass after the ban is lifted or lapses. `getSubjectState` on `at://<did>` shows `moderation.state` `removed` while in force and `clear` after lapse, and `localRemoval` (with `expiresAt` for a temporary ban) while the decision is active. Account actions appear in `listActions` and `listAdminActions` with the `at://<did>` subject, the acting admin and `expiresAt`, under the same reason-withholding rules, and never with a content snapshot.

### What a ban hides

While a ban is in force, every viewer other than the account itself, signed in or not, stops seeing the account's content. Its posts drop out of the timeline, community feeds, search, Discover and `actor.getPosts`, `community.post.get` returns them as not found, and `actor.getComments` lists nothing. Its comments in threads, subtrees and permalinks are removed placeholders (`deletionReason` `moderator`, an instance-scope source naming the instance DID) with replies kept. Notifications whose record, subject or root post is the account's read `removedByServerAdmin` for every recipient but the account ([NOTIFICATIONS.md](NOTIFICATIONS.md) § Moderated accounts and communities). `actor.getProfile` returns the suspended shape: `did`, `handle`, `createdAt`, `accountStatus` `suspended` and zero post and comment counts, with no display name, description, avatar or banner. The account itself still sees all of its own content and its full profile, plus a `banNotice` (`reason`, and `expiresAt` for a temporary ban), which `actor.getViewerAuthority` also carries. These are read-time checks on the database clock (`accountRestrictedSQL`), so an unban or a temporary ban reaching `expiresAt` restores everything they hid, with nothing written. Per-item removals are independent and stay in place after an unban.

Coves cannot refuse comments and votes the account writes straight to its PDS while banned, so the consumers record them hidden with `hide_reason` `account_ban` (migration 073) when the ban is in force at Coves index time on the consumer clock, in every community and before any pending community check. Like `community_ban` the marker is permanent: those comments stay placeholders for everyone and those votes stay out of tallies after an unban or lapse, and replays keep it. Only content Coves indexed before the ban or after it ended is served and counted again. Index-time classification holds the ban-subject advisory lock on the author's DID, which `banAccount` and `unbanAccount` also take, so a ban's commit and a classification serialize.

## Account status restrictions

An account whose PDS reports it `takendown` or `suspended` is restricted on this instance like an account under an in-force ban, for reads and community roles only. The users consumer handles `#account` events with `active` false and one of those two statuses, and activations (`active` true) of an account that has a stored restriction; other statuses are ignored, and an activation with nothing stored asks no PDS. Jetstream delivers `#account` for the whole network, and a takedown or suspension for a DID with no Coves presence (a `users` or `communities` row, or an authored post or comment) and no stored restriction is confirmed and stored like any other, at the cost of one PDS call per network takedown: content the account wrote before its takedown can still be indexed afterwards (the users, posts and comments connectors run independently, and the redrive lane can index an earlier commit later), and the stored restriction hides it. A failed confirmation for such a DID stores nothing and keeps no recheck row, so it is not retried. The event only triggers a check: the consumer asks the account's current PDS (`com.atproto.sync.getRepoStatus`, uncached identity resolution, SSRF-safe client, 5-second timeout) and applies only the confirmed answer, storing the status in `account_status_restrictions` (migration 074) or deleting the row. A 400 answer naming `RepoTakendown`, `RepoSuspended` or `RepoDeactivated` counts as that inactive status: `getRepoStatus` declares only `RepoNotFound`, but PDSes use these names from the sibling `com.atproto.sync` lexicons (`getRepo`, `getLatestCommit`). Any other error name, or these names under another status, is an error status. A forged or stale event cannot set or lift a restriction. Each DID's read, confirmation and write run under one per-DID lock.

While the row exists, every read that hides a banned account's content hides this account's too (`accountRestrictedSQL`): posts, comments, notifications and the suspended profile shape, with the account itself still seeing everything. It gets no `banNotice`, and no Coves write is refused except that its community roles are suspended while the row exists, as under an in-force ban ([COMMUNITIES.md](COMMUNITIES.md) § Owner authority). Comments, edits and active re-creates the account's PDS still delivers while restricted send no reply or mention notifications, but carry no `hide_reason`; its late votes still count. Deleting the row is the whole restore: nothing was rewritten, so nothing needs undoing.

A confirmation that fails (identity unresolved, PDS unreachable, an error status, or an invalid answer) keeps the stored state and writes a row in `account_status_rechecks` (migration 076) with the failure code; the event is consumed. A repo-not-found answer over a stored restriction is treated the same way: the restriction stays and the row is rescheduled with code `repo_not_found`; with nothing stored it changes nothing and clears the row. PDSes emit `#account` only on change, so the recheck worker in `cmd/server` is the retry: every minute it retries up to 50 due rows, fewest attempts first and then oldest due, so a long-failing DID cannot starve newer ones, waiting 1 minute before the first attempt and doubling up to a 1-hour cap. It never gives up; the row goes once the PDS answers, a due row for a DID with no Coves presence and no stored restriction is dropped without asking any PDS, and a newer `#account` event that asks the PDS again supersedes it: its answer clears the row, or its failure restarts the backoff. The exception is an activation of an account with no stored restriction: it asks no PDS and keeps the pending row, so a forged active event cannot cancel a pending takedown check. Each pass with due rows logs its due, confirmed, failed and dropped counts at Info; a pass cut at the 1-minute cycle deadline logs them at Info too, a pass ended by shutdown is not logged as a failure, and any other failed pass logs at Error.

## Community removal

`removeCommunity` and `restoreCommunity` take a community DID (`subject`), `expectedVersion`, `idempotencyKey`, `reason` and an optional `privateNote`, behind `RequireInstanceAdmin` like `banAccount`. A subject that is not a DID is InvalidRequest. `removeCommunity` on a DID that is not an indexed community is InvalidSubject; `restoreCommunity` lifts an active community removal even when the community row was deleted, and with none, a DID that is not an indexed community is InvalidSubject. The moderation subject is `at://<did>`, read and version-checked through `getSubjectState`. Removing an already-removed community at the current version is unchanged, with nothing written. Removing a community whose DID has an account ban in force is StateConflict (unban it first); a lapsed ban is superseded by the removal. Restoring a community with no active removal is StateConflict, and it never reverses an account ban, and doxing and illegal-content are refused on a restore with UnsupportedReason. Reusing an idempotency key across the two procedures is IdempotencyConflict. Both actions appear in `listActions` and `listAdminActions`.

A removal is one `remove` action and the instance removal decision on `at://<did>`, with a `!takedown` label on the bare community DID. A restore records a `restore` action, deactivates the decision and writes the `neg`. Coves does not take the community's account down on its PDS.

While the removal is active:

- `community.get` still answers 200 with `did`, `handle`, `name`, `displayHandle` and `status` `removed`, and withholds the display name, description, description facets, avatar and banner.
- The community drops out of `community.list`, community search and Discover.
- Post create (every author class, aggregators included), comment create on its threads, vote create on its posts and comments, and subscribe are refused with 403 `CommunityRemoved` before any PDS write or ledger reservation. A comment is checked against the community of its indexed parent, the same resolution as the community ban check. Existing subscriptions stay in place.

These are read-time checks, so a restore brings everything back with nothing else written. The firehose acceptance engine does not decide a post in a removed community: its decider returns undecided (`ErrCommunityRemovedDeferred`, counted as deferred), and `ListPendingSubjects` leaves the community's `pending` and `pending_reacceptance` rows out of the batch. Posts written straight to a PDS, and edits of accepted posts, wait in those states during the removal and are decided as usual after the restore, so the removal never becomes a rejection or a signed removal commit. The community's existing content is hidden at read time too: its posts drop out of every read path for every viewer but their author, whose profile posts, thread header and `post.get` keep them with admission status `removed` and no community avatar, and comments whose parent chain reaches one of its posts are listed in profile activity only to their commenter. Notifications about either read `removedByServerAdmin` for every recipient but the author. Community suggestions have no link to an indexed community, so a removal changes nothing there.

A community removal and an account ban are stored the same way (an instance removal decision on `at://<did>` naming no collection), and each action records which it is in `subject_kind`, `community` or `account` (migration 075). Readers and mutations key on the recorded kind, never on whether the DID has a `communities` row or whether the decision has an expiry. Migration 075 backfilled the kind with the rules readers used before: a removal with an expiry is an account ban, a permanent one is a community removal when the DID has a `communities` row and an account ban otherwise, and a restore has the kind of the action it reverses. Its down migration refuses while any recorded kind differs from that rule, while any account action is on a DID that has a `communities` row, or while a restore's kind differs from the action it reverses. A community-kind action never has an expiry (a CHECK constraint).

The community consumer refuses (`ErrPermanentEvent`) a community profile from a DID with account activity: a `users` row whose `index_source` is `account`, or an authored post, comment or vote. A `users` row written only by post-author hydration (`index_source` `author_hydration`, migration 075, which also backfilled it for existing rows whose DID has a `communities` row) does not count: the authored post counts on its own, and the row outlives it when the post cascades away with a deleted community. Signup, sign-in, aggregator registration and a profile record indexed from the firehose write or upgrade the row to `account`; profile and handle updates leave the source alone. The exemption is a trusted bridge's community: the resolved PDS is a trusted bridge host and the verified handle is under that host's registrable domain (a bridged group posts as itself before its profile arrives). The PDS alone never exempts, since the DID controller writes it in its own DID document, and the record's own origin or `hostedBy` never exempts it. `banAccount` applies the same rule to the stored community `handle` and `pds_url`. User creation and the firehose post, comment and vote consumers hold the ban-subject advisory lock on the DID, which the community create takes before its check, so a concurrent write from them is either seen or waits; `cmd/reindex-votes` and the repository-level post, comment and vote `Create` methods do not take it. A footprint-free DID can still index as a community. An account ban made on it before it is indexed keeps reading as an account ban; after indexing, `banAccount` refuses the DID (`InvalidSubject`) until it gains account activity, and otherwise it is moderated with `removeCommunity`.

If a removed community's row is deleted (its profile record is deleted), the leftover decision still reads as a community removal, and `restoreCommunity` lifts it.

### Runbook: a community refused because of a pre-075 hydrated author row

Migration 075 marked `users.index_source = 'author_hydration'` only for DIDs that already had a `communities` row. A users row that post-author hydration wrote before 075 for a community DID with no `communities` row at deploy (its posts arrived before its profile, or the community was deleted before the deploy) is `account`, so the community's profile is refused. The backfill is deliberately not widened; fix such DIDs one at a time.

1. **Recognize it.** The AppView logs `security: refusing community profile from a DID with account activity` with `did=<did>`, and the event is dead-lettered already exhausted (`attempts` = 10) under consumer `communities` (or `communities@<feed>`):
   ```sql
   SELECT id, consumer_name, attempts, last_error, updated_at FROM jetstream_dead_letters
   WHERE consumer_name LIKE 'communities%' AND last_error LIKE '%community DID has account activity%'
     AND last_error LIKE '%<did>%';
   ```
2. **Check the evidence outside the database first.** Before starting the repair, confirm the DID is not an account: it has no `social.coves.actor.profile` record (`com.atproto.repo.listRecords` on its PDS) and was never a Coves user (signup history). The database keeps no record of a past sign-in, since sessions are deleted on logout. Any of these means it is an account; stop.
3. **Check and reclassify in one transaction.** Take the ban-subject lock first, so sign-in, user creation and the post, comment and vote consumers wait, then check, then update:
   ```sql
   BEGIN;
   SELECT pg_advisory_xact_lock(hashtext('community-ban-subject:' || $1));
   -- Every count must be 0 except users_account (1).
   SELECT
     (SELECT COUNT(*) FROM users WHERE did = $1 AND index_source = 'account') AS users_account,
     (SELECT COUNT(*) FROM posts WHERE author_did = $1) AS posts,
     (SELECT COUNT(*) FROM comments WHERE commenter_did = $1) AS comments,
     (SELECT COUNT(*) FROM votes WHERE voter_did = $1) AS votes,
     (SELECT COUNT(*) FROM oauth_sessions WHERE did = $1) AS oauth_sessions,
     (SELECT COUNT(*) FROM aggregators WHERE did = $1) AS aggregator,
     (SELECT COUNT(*) FROM communities WHERE did = $1) AS community;
   UPDATE users SET index_source = 'author_hydration'
   WHERE did = $1 AND index_source = 'account'
     AND NOT EXISTS (SELECT 1 FROM posts WHERE author_did = $1)
     AND NOT EXISTS (SELECT 1 FROM comments WHERE commenter_did = $1)
     AND NOT EXISTS (SELECT 1 FROM votes WHERE voter_did = $1)
     AND NOT EXISTS (SELECT 1 FROM oauth_sessions WHERE did = $1)
     AND NOT EXISTS (SELECT 1 FROM aggregators WHERE did = $1)
     AND NOT EXISTS (SELECT 1 FROM communities WHERE did = $1);
   COMMIT;
   ```
   If any count is not as expected, run `ROLLBACK` instead of the UPDATE and stop. An authored post means the community's posts are still indexed, and the refusal is the account-activity rule working as intended unless the DID is a trusted bridge's community. A current `oauth_sessions` row means it is an account. The UPDATE repeats every check in its `WHERE`, so it must report `UPDATE 1`; on `UPDATE 0` a signal is present, so run `ROLLBACK` and stop. The lock expression is `communities.BanSubjectLockKeySQL` (`internal/core/communities/community_ban.go`); use that one if it has changed.

   A sign-in or signup after the commit upgrades the row back to `account` (the `author_hydration` upgrade in user creation, under the same lock), so the repair cannot erase a genuine account; the community profile is then refused again, as it should be.
4. **Re-index the profile.** Reset the dead letter so the redriver retries it on its next pass (`REDRIVE_INTERVAL`): `UPDATE jetstream_dead_letters SET attempts = 0 WHERE id = <id>;`. If the dead letter is gone (pruned seven days after its last attempt), have the community republish its profile record (any `putRecord` of `social.coves.community.profile` with a new rev). Confirm a `communities` row now exists for the DID.

## Public modlog

`listActions` is public and names the acting admin's DID. `listAdminActions` adds private notes and the subjects the public view suppresses. Public fields are built by allowlist in `NewActionView`, never by stripping a private projection.

Q-LABEL-LOG (2026-09-30): `listActions` never returns `label` or `retract-label` actions, and its `action` filter rejects those values with InvalidRequest. The admin log keeps them; the blur on the post is the public signal.

Restricted subject (decided 2026-10-03): removals are public by default. The public log names a subject (URI, CID and the community it was posted in) and matches it under subject, collection and community filters while its post or comment row is indexed, whether soft-deleted or not and whatever its admission status. Only a subject whose row is gone, as after account erasure, is restricted: listed without subject or community, and excluded from those filters.

Content snapshots (decided 2026-10-13): a removal stores the text of the version the admin removed, as `contentSnapshot`: a post's title, body and external link URL, a comment's body, and `capturedCid`, the CID it was read from. Restores and labels store none, and illegal-content removals store none at all. A restore entry shows the snapshot of the removal it reverses, under the same public rules. A label or retract-label entry (`listAdminActions` only) shows the post's current title, body and external link URL, with `capturedCid` its current CID; it has none when the post is deleted by its author, gone, or has a doxing or illegal-content action. A doxing or illegal-content removal also deletes every snapshot earlier removals of the same subject stored, for admins too. Removing a comment its author already deleted stores none, because the delete blanked its text. The public log shows the snapshot only with the subject, so it is withheld for doxing removals; `listAdminActions` shows it there. A restricted subject has no snapshot left: its row is gone only after account erasure, which also deletes the author's snapshots. Once the author deletes the subject, the public entry still names it but withholds the snapshot; `listAdminActions` keeps it. For a comment this is permanent: a new record that re-creates the comment's URI does not bring the snapshot back. The snapshot is kept while its action row exists, and a restore or a later edit does not change it; a label entry's text follows edits. Erasing the author's account deletes the author's snapshots and keeps the actions. The author is the account that wrote the post or comment, which for a legacy post is not the community repository that holds it.

Community entries (2026-11-16): the log lists community-scope actions with the instance ones, and `community=<did>` returns both for that community. `scope.kind` says whose authority an entry is (`instance` or `community`). The actor DID is public; `adminActing: true` marks a Coves admin acting for a community without a usable community role that permits the action. An entry for a record written outside Coves, such as a role, removal or ban record found on the firehose with no matching intent, has no actor. Roster entries (`grant-role`, `remove-role`, `transfer-ownership`) name the account as subject `at://<did>` and carry `role`, the role granted, removed or, for a transfer, given to the new owner. Roster actions logged before migration 091 have no `role`.

A community-scope entry whose reason, or whose reversed removal's reason, is doxing or illegal content is withheld like a restricted subject: no subject, CID or `scope.communityDid`, and it is excluded under subject, collection and community filters, and under an authority filter naming the community. Only the subject is withheld, not which community acted: `authorityDid` and `ref.serviceDid` are required and still name the community.

Comment subjects carry `rootUri`, the post at the root of the comment's thread, recorded when the action was taken. A restore copies it from the removal it reverses. Actions recorded before 2026-10-13, and comments whose indexed root is not a valid AT-URI, have none. It is withheld from the public log with the rest of the subject, and on its own when the root post has a doxing or illegal-content action or is no longer indexed; `listAdminActions` then carries it in `privateSubject` (decided 2026-10-13).

## Media blocks

Every removal blocks the (owner DID, blob CID) pair of each image on the subject, on cache hits and misses, and purges the image proxy's disk cache. An illegal-content removal also blocks each CID for every owner, so a re-upload from another account is not served. Restoring deactivates the decision's blocks.

Q-I6 (2026-09-28): every-owner blocks cover only the CIDs indexed when the admin acted. An image the author adds later, by an edit, a recreate or a create the consumer does not index, gets an owner-scoped block only, through `MediaReconciler.ReconcileTx` when the change is indexed and `ReconcileIncomingTx` when it is not. Otherwise an author could get someone else's image blocked for every owner.

The owner is the repo that holds the blob, which is not always the human author. Legacy bridged posts live in a Tidepool community repo, so several legacy posts can share one (community DID, CID) pair, and removing one blocks the image on all of them. This was accepted.

Bluesky media served from cdn.bsky.app is outside Coves' control; removal only stops the AppView from handing out those URLs. Edge purge, cache headers and exposure bounds are in [MEDIA.md](MEDIA.md).

## Writes on removed subjects

Removing a post or comment adds no write-path refusal (decided 2026-09-20). `feed.vote.create` and `comment.create` forward to the author's PDS without looking up the subject's removal, and the consumer indexes votes and comments that target removed subjects. They stay unserved through the parent's state and appear on restore. Clients hide vote and reply controls on a removed-comment placeholder as they do on an author-deleted one. The refusals that do exist are for the writer or the community, not the subject: an account ban in force, a community ban (POSTS.md § 4.1) and a community removal.

## Idempotency and versions

Every mutation carries an idempotency key and the `expectedVersion` from `getSubjectState`. Keys are scoped to actor DID plus authority DID and bound to a fingerprint of the whole request; reuse with a different body is IdempotencyConflict, and a replay returns the original result, not current state. `MODERATION_IDEMPOTENCY_RETENTION` (default 24h) sets how long keys live, and `MODERATION_IDEMPOTENCY_MAX_LIVE_KEYS` (default 1000) caps live keys per actor; a request over the cap is InvalidRequest. After a key expires, the monotonic version still stops an old retry from reversing newer state.

## Durability

`moderation_*` tables hold decisions, not index state. They have no foreign key to posts or comments, so decisions survive deletes, recreates at the same URI, and reindexing. Backups and any truncate or reindex procedure must keep them.

## Community comment removals

A `social.coves.community.removal` record whose subject is a comment removes that comment when the record is in the repo of the community that hosts the comment's thread root post (the root's indexed `community_did`). A record from any other repo is ignored. Writing the record removes the comment; deleting it restores it. There is no acceptance record. The consumer writes an `apply-removal` action and an active `moderation_decisions` row with the community as authority and `scope_kind = community`, `origin = inherited`, no actor and the record's code mapped to the action reason (`moderation.CommunityRemovalActionReason`, table under § Post remove and restore); the delete writes a `retract-removal` that reverses it, with no actor and the deleted record's mapped code. The record's code and reason are kept on its `community_comment_removals` row (migration 089); a row indexed before 089 has none, and its actions carry `#reasonModeratorDiscretion`. A removal written by a moderator through Coves (§ Comment remove and restore) is recorded once, naming the moderator, whichever of the local completion and the firehose copy comes first. These decisions are independent of instance removals: neither restores the other. The one link is the record an instance removal of a comment writes in a hosted community (§ Scope): the consumer indexes it back as a community-scope decision like any other, and the instance restore's delete of that record retracts it.

A removal that arrives before its comment or its thread root is held in `community_comment_removals` (migration 067), keyed by (repo DID, rkey). Deleting a held record discards it.

The thread root is the post the comment's parent chain reaches, not the comment's own `root_uri`. Removals are reconciled when the removal record is indexed (including a redelivery, which reconciles that record), when the comment consumer indexes a comment (every removal of it and of the comments beneath it), and when the post consumer indexes a post (every removal of the comments beneath it). Reconciling one removal locks its row, then resolves the thread under that lock, then acts on the current state:

- Held, and the thread resolves to the record's community: the removal is applied.
- Applied, and the thread now resolves to another community (the commenter deleted the comment and re-created it at the same URI under another community's post): the removal is demoted to held. Coves writes a system `retract-removal` with no actor, the community as authority, `origin = inherited` and reason `reasonSubjectMoved`, reversing the active `apply-removal`, and ends the decision. The public log shows the entry without an actor.
- Held after such a demotion, and the thread resolves to the record's community again (the comment came back): the removal is re-applied by a system `apply-removal`, again with no actor and reason `reasonSubjectMoved`, reversing the demotion.
- The chain does not resolve (a parent comment or the post is not indexed, or the chain loops): nothing changes. A held removal stays held, and an applied removal stays applied, so a comment re-created under a dangling parent does not reappear.

Because the row lock is taken before the thread is read, an application that is still writing when the comment is re-created elsewhere is waited on by the re-creation's reconcile, which then sees the applied removal and the new thread and demotes it.

A removal from a repo that is not the thread's community is held indefinitely. There is no prune: a held row may be a legitimate removal waiting for its comment or its root post, and a comment shown under another community's post may come back under the removing community's post. The rows are bounded by the community's own record writes, one per (community, comment), since the record key is derived from the subject.

Authority follows the thread. When a comment's parent is re-created under another community's post, the removing community's removals of the replies beneath it are demoted as well, and the new thread's community can remove them.

`getComments` serves a community-removed comment as a moderator-removed placeholder with replies kept, attributed to the community (`scope.kind = community`, `scope.communityDid`). In the author's own profile activity the comment stays listed with its content and the same attribution; other viewers do not see it there. An instance removal hides the comment from its author too.

This is the Coves half of comment removal across the Lemmy bridge: Tidepool writes these records in the bridged community's repo when a Lemmy moderator removes a comment. Until Tidepool ships that writer, a Lemmy moderator's comment removal stays visible here.

## Community moderation: state and versions

Each community moderation subject has a version in `community_subject_versions` (migration 083), keyed by (community DID, subject). The subject is a post URI, a comment URI, a banned account's DID, or, for the roster, the community's own DID. A missing row is version 0. The version advances on every indexed community record change for the subject (acceptance, removal, ban and role records and their deletes). A moderation client reads a subject's state and version together and can tell whether the community records behind what it read have changed. Two state changes come without a version change: `post.status` also moves through AppView-local states (`pending`, `pending_reacceptance`, `rejected`), and a ban stops being in force at its `expiresAt`. The rows have no foreign key; deleting a community deletes them in the same transaction.

An index change advances the version by exactly one, in the transaction that makes the change, so a failed version write rolls the change back. A change that writes no row advances nothing: a rev-gated stale or equal-rev replay, a refused admission watermark, a delete of a record whose row is already gone, or a role record rewritten with the same role, record key and CID. The changes that advance it:

- Post: a community acceptance or removal record, its delete, or a bridged-stats repin, written to `community_post_admissions` from the firehose, the acceptance engine, the community record write queue or a moderator's remove or restore. A remove or restore commit changes two records (the acceptance and the removal) and advances the version once. The AppView's own observations (the pending row at post creation, an author edit, a local rejection) do not advance it, so a post remove or restore whose `expectedVersion` was read before such a move does not conflict.
- Comment: each change to the community's effective removal decision. Applying a removal (directly, or a held one when its comment or root arrives), retracting it when its record is deleted, and demoting it when the comment moves to another community's thread each advance once. Indexing or discarding a held record changes no decision and advances nothing.
- Account: indexing a community ban record, or deleting an indexed one.
- Roster: creating, rewriting or deleting a role record.

Local writes index at their commit rev. The acceptance engine and the community record write queue stamp the commit rev on the admission watermark, so the firehose copy of the same commit is refused. A role record this instance writes is indexed with `UpsertCommunityRoleAtRev`, which first claims the record's rev gate (`jetstream_record_revs`) at the commit rev and writes nothing when the firehose already handled that rev or a newer one. Either way, one commit advances the version once. `CreateCommunity` indexes the creator's owner record this way at the rev of the commit that wrote it; on a resumed create whose identical owner-record put commits nothing (`pds.ErrNoCommit`), it indexes nothing locally and leaves the earlier attempt's firehose event to index the record.

`social.coves.moderation.getCommunityState?subject=&community=` (authenticated) returns `community`, `subject`, `kind` (`post`, `comment`, `account` or `roster`), `version`, and the kind's state: `post.status` (the admission status, or `none` with no admission row), `comment.removed`, `ban` (only while in force: no expiry or a future one) or `roster` (owner and moderators by the owner rule). A post or comment subject's community is the one it is indexed under, and any `community` parameter is ignored; a DID subject needs `community`, and the community's own DID reads the roster. The caller must be a moderator or owner of that community, or an instance admin, under `communities.RoleAuthorizer`; anyone else gets `Forbidden`.

## Community moderation: actions

Community-authority actions (a moderator resigning, the owner or an admin removing a moderator, accepting an invitation, which grants the moderator role or transfers ownership, a moderator removing or restoring a post or a comment, and banning or unbanning an account) run through one pipeline, `moderation.CommunityActionService` (`internal/core/moderation/community_actions.go`, accept in `community_invitations.go`), over the store `postgres.CommunityActionRepository`. Inviting, offering ownership and declining (`moderation.CommunityInvitationService`) write nothing to the community repo: they take the same locks and run steps 1-7 in one action transaction, then store the invitation change and the idempotency record and commit.

Pipeline order, per request:

1. Validate the request (empty actor `AuthRequired`; community and subject DIDs, invitation ID and idempotency key 1-128 bytes, `expectedVersion >= 0`, otherwise `InvalidRequest`). An invitee given as a handle resolves through the configured identity resolution: an unknown handle is `AccountNotFound`, an invalid one `InvalidRequest`, any other failure `ModerationUnavailable`.
2. Resolve the community: the `community` parameter for roster actions and invitations, the invitation's community for accept and decline, which read the invitation first and refuse one addressed to another account as `InvitationNotFound` (post actions take it from the indexed post, the one read allowed before authorization).
3. Authorize through `communities.RoleAuthorizer` (resign needs moderator, remove, invite and offer need owner, which admins satisfy; accept needs the community hosted and not removed; decline only the invitation). A refusal or a removed community is `Forbidden`, any other failure `ModerationUnavailable`, and nothing else is read first.
4. Open the action transaction and take its locks (below).
5. Recheck authorization under the locks. A moderator removed while its request waited is refused here.
6. Idempotency: a stored result for (actor, community, key) with the same request is returned unchanged, a different request is `IdempotencyConflict` (also when the key names another request's open intent), and an open intent for the key is reconciled (below). Invite, offer and decline write no intent; they refuse with `StateConflict` while an accept of one of the invitee's invitations in the community has an open intent, since its write may have committed. An open intent of another key on a target record (as its target or a transfer's paired target), and for an ownership accept any open `transfer-ownership` intent in the community, is settled as the sweep settles it (below), committed, and the request restarts from step 4; its writer's locks are gone, so it can only be awaiting reconciliation, and while it is unexpired with the head still at its guard the request is `StateConflict` instead. A caller refused by authorization still gets its own stored result for the same key and request, since its action may have removed its authority.
7. Apply the action's rules (owner cannot resign, owner's record cannot be removed, the subject must hold a role; an invitation open and not lapsed for accept and decline, the invitee not banned and the roster rules for invite, offer and accept), then require the roster version to equal `expectedVersion` (`StateConflict`). An accept plans its writes from the roster read under the locks: when they need a lock the attempt does not hold (an admin's offer on a community with an owner rewrites the owner's record), it restarts from step 4 under the union of both locks.
8. Read the community repo through the community repo factory (`EnsureFreshToken`): the head commit, then each target record. For a delete, a missing record while the row is indexed is `StateConflict`, logged at error level: no open intent explains it, so the index missed the record's delete. For a create or update (`requireRepoMatchesIndex`), a record present but not indexed, or indexed but absent, is `StateConflict`. A record whose CID differs from the indexed row is `StateConflict` (the index is behind).
9. Store the intent, committed on its own before the write. A second open intent on a record, as a target or a paired target (a concurrent request that slipped past step 6), is refused by the index as `StateConflict`.
10. Write with `applyWrites` under `swapCommit` = the head read in step 8: one write, or for a transfer with an owner the invitee's owner record and the previous owner's record rewritten as moderator in one commit.
11. On success, apply the local effect in the action transaction and commit (`CompleteIntent`): claim every target's rev gate at the commit rev the PDS returned; for a delete drop the index row if it still has the replaced CID; for a create or update index each record from the intent's body at the CID the PDS returned; advance the roster version once, insert one action (actor, `admin_acting`; an accept's actor is the inviter), mark the invitation accepted, mark the intent completed and save the idempotency record. A `swapCommit` refusal (another writer moved the head) committed nothing: the intent is marked `failed` and the request fails with `StateConflict`; on a same-key retry an earlier attempt may have committed since, so the intent is settled from the repo instead. On any other PDS error the outcome is unknown: the transaction rolls back, the intent stays open and the request fails with `ModerationUnavailable`.

Restarts are bounded: each restart that widens the locks must hold strictly more than the attempt before (the locks only grow, so widening ends), and one restart after settling an open intent is allowed; a widening that adds nothing or a second settled intent is `StateConflict`, logged at warn level.

### Post remove and restore

`social.coves.community.removePost` (`subject`, `code`, optional `reason`, `expectedVersion`, `idempotencyKey`) and `social.coves.community.restorePost` (`subject`, `expectedVersion`, `idempotencyKey`) are authenticated procedures (`internal/api/handlers/moderation/community_posts.go`, routes `routes.RegisterCommunityPostRoutes`). They run `CommunityActionService.RemovePost` and `RestorePost` (`internal/core/moderation/community_post_actions.go`). A remove makes one commit that deletes the community's acceptance (when one stands) and creates or updates its removal record `{subject: {uri, cid}, code, reason, createdAt}`; a restore makes one commit that deletes the removal record and writes an acceptance pinned to the post's current CID. The writes go through `posts.CommunityRecordWriter` (`WriteRemoval`, `RestoreAcceptance`) with the community's credentials. The output is `uri` (the removal record for a remove, the acceptance for a restore), `version`, `actionId` (absent when nothing was written) and `alreadyApplied`.

Order, per request:

1. Validate: empty actor `AuthRequired`; `subject` must be a record AT-URI with a DID authority, `idempotencyKey` 1-128 bytes, `expectedVersion >= 0`; for a remove, `code` must be a removal record code (`rule-violation`, `spam`, `off-topic`, `illegal-content`, `author-banned`, `moderator-discretion`, `harassment`, `doxing`; the record carries it verbatim) and `reason` at most 1000 graphemes and 10000 bytes. Anything else is `InvalidRequest`, with nothing read.
2. One lookup: the community the post is indexed in (an undeleted post with an admission row). A post not indexed in a community is `PostNotFound` (404). The request carries no community field.
3. Authorize with `communities.RoleAuthorizer` at the moderator role (owner, moderator or instance admin; the community hosted here and not removed; an in-force instance ban refuses). A refusal is `Forbidden`, with no other read.
4. Open the action transaction and take its locks (§ Locks and the one lock order: the actor's erasure gate, the roster lock, the actor's account lock and the rev-gate rows of the post's removal and acceptance records).
5. Recheck authorization under the locks. A moderator whose role was removed while the request waited is refused here, and nothing is written.
6. Idempotency, as in step 6 above: a stored result is replayed, an open intent for the key is reconciled, and another key's open intent on the post's removal record is settled first.
7. Read the post's state in the transaction (`CommunityPost`): `StateConflict` if the post moved to another community, or if the post subject's version in `community_subject_versions` is not `expectedVersion`. Only the community-record version is compared: a `post.status` move made locally (`pending`, `pending_reacceptance`, `rejected`) leaves the version and does not conflict.
8. Rate limits, for a remove by an actor who is not acting as an instance admin (below).
9. Pre-read the community repo: the head commit, then the acceptance and the removal record under the post's subject key. The repo must match the index: an acceptance stands exactly when the index holds one, pinning the same CID, and the removal record's CID is the one in `community_post_removal_records`. A removal indexed before migration 088 has no CID there and matches any removal the repo holds; a removal in the repo the index has not applied is a mismatch. A mismatch is `StateConflict` (the index is behind). A restore with no removal standing is `StateConflict`, unless an acceptance already pins the post's current CID; then the writer skips (below).
10. Store the intent (§ Intents and reconciliation) with the stand-record body: the removal for a remove, the acceptance for a restore. A record the write creates carries the intent's time as `createdAt`; an update keeps the standing record's.
11. Write. Before each batch is sent, the writer's `BeforeCommit` records the attempt in its own transaction (`community_write_intent_attempts`: the guard head used as `swapCommit`, the stand record's CID before the batch, `""` for a create, and the exact body). A failure to record it sends nothing.
12. Apply the local effect in the action transaction (`CompleteIntent`): the admission change through the shared admission functions, the code and reason on the admission row, the commit rev on its watermark (so the firehose copy is no new change), the removal record indexed in `community_post_removal_records` (or dropped, for a restore), the post's version advanced once, one action, the intent completed and the idempotency record saved. The action is `remove` or `restore`, scoped to and authored by the community, with the actor and the admin-acting mark, origin `local`, and the reason mapped from the removal's code (for a restore, the code of the removal it deleted).

Rate limits: a remove is refused with `RateLimited` (XRPC 429 `RateLimitExceeded`) before any repo read or write and before any intent when either count over the last hour has reached its limit. `COMMUNITY_REMOVALS_PER_MODERATOR_PER_HOUR` (default 60) and `COMMUNITY_REMOVALS_PER_COMMUNITY_PER_HOUR` (default 300) set the limits; each must be a positive integer or boot fails. `RecentCommunityRemovals` (`internal/db/postgres/community_post_action_repo.go`) counts, in the post's community, the `remove` actions with origin `local` and not admin-acting created in the window, plus the open, not admin-acting remove intents created in the window. The per-community count is all of those; the per-moderator count is those whose actor is the requesting moderator, so it is per moderator per community: removals the same moderator makes in another community do not count. Removals by an actor acting as an instance admin are neither limited nor counted, restores are not limited, and firehose-indexed removals are not counted. The roster lock serializes the count with the intent that reserves the removal.

Skipped writes: the writer writes nothing when an identical removal already stands (the same code and reason; the pinned CID is not compared) and no acceptance is left to delete, or, for a restore, when no removal stands and the acceptance already pins the post's current CID. The service then decides from the intent's latest recorded attempt. When an attempt was recorded and the standing record's CID differs from the CID the attempt recorded before the batch, the commit is this intent's (an earlier request's response was lost): it completes as in step 12 at the attempt's guard rev. Otherwise the decision was already in place: the result is `alreadyApplied` with the current version, the idempotency record is saved, the intent closes as `failed` with no action, and no admission row, version or existing action changes. The skip's head rev is never recorded as the intent's commit rev.

The removal code to action reason mapping (`moderation.CommunityRemovalActionReason`), used for local actions, firehose-indexed removals and the restores that delete them:

| Code | Action reason |
| --- | --- |
| `spam` | `#reasonSpam` |
| `rule-violation`, `off-topic` | `#reasonRuleViolation` |
| `harassment` | `#reasonHarassment` |
| `doxing` | `#reasonDoxing` |
| `illegal-content` | `#reasonIllegalContent` |
| `author-banned`, `moderator-discretion`, any other code | `#reasonModeratorDiscretion` |

Independence from instance removals: a community removal and an instance removal of the same post are separate decisions. Restoring either leaves the other in force, and the author sees `#moderatedPost` while the instance removal is active. When an instance removal's outbox (migration 080) wrote the community's removal record, a moderator's restore deletes that record and writes the acceptance like any restore; the instance decision stays active and keeps the post hidden. The instance restore then finds its owned record gone and writes or deletes no community record (the ownership rule in § Scope).

### Comment remove and restore

`social.coves.community.removeComment` (`subject`, `code`, optional `reason`, `expectedVersion`, `idempotencyKey`) and `social.coves.community.restoreComment` (`subject`, `expectedVersion`, `idempotencyKey`) are authenticated procedures (`internal/api/handlers/moderation/community_comments.go`, routes `routes.RegisterCommunityCommentRoutes`) running `CommunityActionService.RemoveComment` and `RestoreComment` (`internal/core/moderation/community_comment_actions.go`). The output is `uri` (the removal record), `version` (the comment subject's community version), `actionId` and `alreadyApplied`. They follow the post order above, with these differences:

- `subject` must be a `social.coves.community.comment` record URI. The one lookup before authorization is the community of the post the comment's parent chain reaches (`postgres.NewCommunityCommentResolver`, never the comment's `root_uri`); a comment not indexed, deleted, or whose chain does not resolve is `CommentNotFound` (404).
- The write is one commit with one op on the removal record and nothing on an acceptance (`posts.CommunityRemovalRecordWriter`): a remove creates or updates it, a restore deletes it. An identical removal standing is `alreadyApplied` for a remove; no removal standing is `alreadyApplied` for a restore. The repo's removal record must have the CID `community_comment_removals` holds, else `StateConflict`.
- The intent stores the comment as its subject (`community_write_intents.subject_uri`, migration 089), which tells comment intents from post intents. A restore's attempt records the removal it deletes and no stand record.
- The local effect (`CompleteIntent`) indexes the removal record with its code and reason and applies it (or retracts and drops it, for a restore), stamps the removal record's rev gate at the commit rev so the same-rev firehose copy is stale, advances the comment's version once and logs one `apply-removal` or `retract-removal` with the moderator (admin-acting mark for an instance admin), origin `local`, the mapped code as reason and the service clock as `created_at`. A rewrite of an applied removal logs a new `apply-removal` and moves the active decision to it. A completion recovered at the attempt's guard rev applies when the gate holds that same rev and leaves a change indexed after it in place.
- Firehose-first recovery: a removal record whose CID is the body of an open comment remove intent's latest batch, or a delete of the removal an open comment restore intent's latest batch deleted, completes that intent with its actor instead of logging an actorless action.
- Rate limits are shared with post removals: `RecentCommunityRemovals` also counts local, not admin-acting `apply-removal` actions on comments and open comment remove intents. Restores are not limited.

### Account ban and unban

`social.coves.community.banAccount` (`community`, `subject`, optional `reason`, optional `expiresAt`, `expectedVersion`, `idempotencyKey`) and `social.coves.community.unbanAccount` (`community`, `subject`, `expectedVersion`, `idempotencyKey`) are authenticated procedures, and `social.coves.community.listBans?community=&limit=&cursor=` an authenticated query (`internal/api/handlers/moderation/community_bans.go`, routes `routes.RegisterCommunityBanRoutes`). They run `CommunityActionService.BanCommunityAccount`, `UnbanCommunityAccount` and `ListCommunityBans` (`internal/core/moderation/community_ban_actions.go`). The caller must pass `communities.RoleAuthorizer` at the moderator role: the owner, a moderator, or an instance admin, in a community hosted here and not removed; anyone else gets `Forbidden`. An admin with no role of its own is recorded as admin-acting. The output of a ban or unban is `uri` (the ban record), `version` (the subject's community version, the `account` kind of `getCommunityState`), `actionId` (absent when nothing was written) and `alreadyApplied`. A subject that holds a role is 409 `SubjectHoldsRole`, `StateConflict` and `IdempotencyConflict` are 409, `RateLimited` is 429 `RateLimitExceeded`.

Validation, with nothing read: `reason` at most 2000 graphemes and 20000 bytes (the `ban` record's limits); `community` and `subject` DIDs, and the subject not the community itself; the idempotency key and `expectedVersion` as in step 1 above. `expiresAt` is normalized to UTC whole seconds, the precision the record carries, and that value is used in the request fingerprint, the record and the index. It must be after the service clock, or the call is `InvalidRequest`; this check runs after the idempotency replay and the reconciliation of the key's own open intent (step 6), so a retry of a ban whose expiry has since passed gets its result.

Each request takes the roster lock, the actor's account lock, the ban record's rev-gate row and the subject's ban-subject lock (§ Locks and the one lock order), then rechecks authorization and runs idempotency as in step 6. Another key's open intent on the ban record is settled first. A ban then refuses, from the roster read under the locks, a subject that holds a role in the community (the owner, a moderator, or the acting moderator itself) with `SubjectHoldsRole`, and refuses with `StateConflict` while an acceptance of one of the subject's invitations in the community has an open intent, since that write may have committed. An accept refuses with `StateConflict` while a ban of the invitee has an open intent (`refuseUnresolvedBan`, a read of the intent row without `FOR UPDATE`, because the ban consumer locks that row before the ban-subject lock), next to its `InviteeBanned` check. Both read under the subject's ban-subject lock, which an accept and a ban each hold through their PDS write, so the two serialize and no account ends with a role and an in-force ban: whichever commits first makes the other refuse. Unban has no role check. The subject's version must equal `expectedVersion` (`StateConflict`).

The record is `social.coves.moderation.ban` at `communities.BanRecordKey(subject)` in the community's repo, `{subject, reason, expiresAt, createdAt}`, with `reason` and `expiresAt` left out when absent and `createdAt` the intent's time. A ban creates it, or updates the standing record (a new reason or expiry, and a new `createdAt`) guarded by the pre-read CID check and `swapCommit`; an unban deletes it. One commit carries the one op under `swapCommit`. Before the write, the repo's ban record CID must equal the indexed row's (both absent counts as equal), else `StateConflict`.

Already applied: a ban whose identical record stands (same reason and expiry, in force or lapsed) and an unban with no ban row write nothing, log no action, return `alreadyApplied` with the current version and store the result under the key. An unban of a lapsed ban (expiry past, row still indexed) deletes the record like any unban. The same key with a different reason or expiry is `IdempotencyConflict`, against a stored result or an open intent.

Rate limits: a ban that would write, by an actor not acting as an instance admin, is refused with `RateLimited` before any repo read and before any intent when either count over the last hour has reached its limit. `COMMUNITY_BANS_PER_MODERATOR_PER_HOUR` (default 60) and `COMMUNITY_BANS_PER_COMMUNITY_PER_HOUR` (default 300) set them; each must be a positive integer or boot fails. The budget is separate from removals. `RecentCommunityBans` (`internal/db/postgres/community_ban_action_repo.go`) counts, in the community, local not admin-acting community-scope `remove` actions on an account subject in the window (a rewrite of a standing ban counts) plus open, not admin-acting ban intents created in the window, whatever their expiry, until they settle; the per-moderator count is those by the requesting moderator. `RecentCommunityRemovals` does not count ban intents. Admin-acting bans are neither limited nor counted, unbans are not limited, and firehose-indexed bans are not counted. The roster lock serializes the count with the intent.

Local effect (`completeBanIntent`, in the action transaction): stamp the ban record's rev gate at the commit rev, then index the ban with its reason and expiry (or drop the row, for an unban), write the ban history and advance the subject's version once when the index changed. When the gate already held a later change to the record, that change stands and only the action is logged. One action names the actor: `remove` for a ban (with `expiresAt`), `restore` for an unban with `reverses_action_id` set to the subject's latest ban action in the community when that is a `remove`. An unban that finds its record already lifted links to the `restore` already logged for the deletion of that record (matched by the record key and the replaced CID, which every ban action stores in `role_record_key` and `role_record_cid`); a restore of any other record at the key, such as a later ban written and deleted outside Coves, is not its own, and it logs its own `restore`. Ban actions are scoped and authored by the community, with `subject_uri = at://<subject DID>`, `subject_kind = account`, no collection, origin `local`, the admin-acting mark, and the reason `social.coves.moderation.defs#reasonModeratorDiscretion`. The free-text reason is in the ban record and the index, shown to the banned account, and never in the action log.

`listBans` returns the community's indexed bans, in force and lapsed, newest indexed first (`postgres.CommunityBanLister`): `subject`, `uri`, `cid`, `reason`, `expiresAt`, `indexedAt` and `active` (no expiry, or one after the service clock). `createdAt` is never set, since the index does not store it. `limit` is 1-100 (default 50); a cursor the lister did not issue, or one over 500 bytes, is `InvalidRequest`. Only the moderator-role check above authorizes it.

Ban intents are reconciled like role intents (§ Intents and reconciliation) and converge with their firehose copies (§ Firehose convergence).

### Locks and the one lock order

Every community-authority action takes its locks in this order, all transaction-scoped, and actions in later changes follow it:

1. the shared erasure gates (`ErasureGateTx`: the shared lock and the marker check), in ascending DID order and once for a repeated DID, of every account in lock 3 and of the gate-only accounts (`ErasureGateDIDs`): every party whose role record or invitation the action can write, including a transfer's previous owner and an invitation's inviter and invitee. An accept takes its inviter's gate without the inviter's account lock, and settling an accept intent (`intentLock`, and the role consumer completing one) takes the gate of the intent's audit actor, the inviter, because the inviter's erasure deletes the invitation the completion marks accepted. `CreateInvitation` takes the inviter's and invitee's again (already held). Two invitation writes do not hold the inviter's gate: a decline takes only the invitee's (its actor), and an invite or offer that supersedes the invitee's earlier open invitation does not take that invitation's inviter's. Both are safe: neither waits outside Postgres while it holds the invitation row, neither takes a lock or row the inviter's erasure holds, and both update only a row still `open` (`SetInvitationState` and the supersede `UPDATE ... AND state = 'open'`). Either the erasure's invitation delete waits on the row until the decline or invite commits and then deletes it, or the decline's locked read waits on the erasure and finds no invitation (`InvitationNotFound`) and the supersede skips the deleted row. Taking them first is safe because account erasure, while it holds the exclusive gate, takes none of locks 2, 3, 4 or 5; they must come before any invitation row (lock 8) and any role row or roster version (lock 9), which erasure deletes or advances in that order (invitations, then `community_roles`, then versions, then role record delete queue rows). Erasure locks no intent row: it marks the open intents whose records name the account (`community_write_intent_erasures`) from a plain read, and each completion reads those marks after taking the gates. Without the inviter's gate, an inviter's erasure that had locked a subscribed community's row could wait on the invitation row an accept holds while the accept waits, outside Postgres, on its credential refresh (step 8) updating that community row: a cycle the deadlock detector cannot see. An erased subject gets no role row and no version change, and in a hosted community the written record's repo delete is queued at its CID ([COMMUNITIES.md § Account erasure](COMMUNITIES.md#account-erasure)); an invite or offer naming an erased inviter or invitee writes nothing (`AccountNotFound`);
2. the per-community roster advisory lock, `hashtext('community-roster:' || community)`, for every action transaction: resign, remove, invite, offer, accept, decline, ban, unban and the sweep. Only the read that serves an authorization-refused caller its stored result takes no roster lock, just the caller's erasure gate (lock 1) and account lock (lock 3);
3. the per-(community, account) advisory locks, `hashtext('community-actor:' || community || ' ' || did)`, in ascending DID order and once for a repeated DID, for the actor and every account whose role the action changes: resign and remove the removed moderator, invite and offer the inviter and the invitee, decline the invitee, accept the invitee and, for a transfer, the previous owner; settling an intent (`intentLock`) takes its requester, its subject and a transfer's previous owner. A ban or unban, and settling its intent, take the actor's lock only, not the subject's. Resign and remove take the removed moderator's lock, so once a removal returns no action by that moderator can still commit;
4. the target records' rev-gate rows in `jetstream_record_revs` (inserted at rev `''` if absent, then `SELECT ... FOR UPDATE`), in ascending URI order: every record the action writes, for a transfer both the invitee's and the previous owner's. Invite, offer and decline write no record and take none;
5. the ban-subject advisory locks (`communities.BanSubjectLockKeySQL`), in ascending DID order: for invite, offer, accept and settling an accept intent, the invitee's, under which its community ban is read; for a ban or unban and settling its intent, the subject's, under which its roles, an open accept intent of its invitations and its ban row are read;
6. the moderation subject row (`LockSubject`, which itself takes the ban-subject lock first, consistent with 5 then 6);
7. the intent rows (`FOR UPDATE`): the key's own intent first, then another key's open intent on a target or an open transfer;
8. the invitation row (`InvitationByID ... FOR UPDATE`), read by accept and decline after the key's own intent row, and an invitation an invite supersedes;
9. index rows.

`lockCommunityAction` (`internal/db/postgres/community_action_repo.go`) takes 1 through 5, in that order, when the transaction opens; the rest are taken by the statements that read them. An accept can hold its invitation row while it locks another key's intent row (7 after 8). That is safe against the role consumer, which locks an intent's row and then its invitation only after holding that intent's gate rows: an accept holds the gate row of the invitee's record first (lock 4), so a consumer completing an intent of the same invitation waits there, and an intent of another invitation never needs the invitation row the accept holds. Invite, offer and decline hold no gate row, but lock an invitation only after refusing while an accept of the invitee's invitations has an open intent, and the roster lock keeps a new one from opening, so the consumer has no intent to complete that touches that invitation.

Action transactions run on their own connection pool (`DB_COMMUNITY_ACTION_MAX_OPEN_CONNS`, default 5, opened by `cmd/server/database.go`), and each holds its connection while it waits on or holds these locks. The holder's other queries take connections from the application pool: authorization, the credential refresh in step 8 and the intent in step 9 (the roster read of step 7 runs in the action transaction). Requests queued on one community's roster lock therefore hold only action-pool connections and cannot exhaust the application pool the holder needs to finish. Nothing inside an action transaction opens a second one.

A post remove or restore takes lock 1 for its actor only, lock 2, lock 3 for its actor only (the post's author is not locked), and lock 4 for the post's acceptance and removal record URIs, in ascending URI order; it takes no ban-subject lock. It then locks intent rows (7) and, in its completion, the post's admission row and its `community_post_removal_records` row (9), and holds all of them through the PDS write and the local transaction. The firehose removal consumer (`ApplyRemovalRecord`, `ApplyRemovalRecordDelete`) takes the same two gate rows first, through `lockCommunityAction` with no roster or account lock, then, for a create or update, the shared erasure gates of the actors of the open remove intents on the record (`gateRemovalIntentActors`, lock 1 after lock 4, which cannot block an erasure since erasure takes no gate row), then the indexed removal record row, an open intent row and the admission row; the comment removal consumer (`RecordRemoval`) likewise takes those gates after the record's rev-gate row and before the comment rows; since an action holds the gate rows from the start, the two serialize on them.

Firehose ingestion takes the gate row, then the erasure gate, the ban-subject lock, the thread root and content rows, and never takes the advisory locks 2 and 3, so the two orders are compatible. The role consumer (`ApplyRoleRecordEvent`) takes no roster or account advisory lock. A create or update with a rev reads, without a lock, the open create or update intent writing the record; when it is an ownership transfer, it locks both of that intent's records' gate rows in ascending URI order (lock 4). It then takes the shared erasure gates of the event's subject and, with an intent, the intent's records' subjects and its audit actor (an accept's inviter), in ascending DID order (lock 1), then claims its own record's gate row. With an intent, `completeWriteIntentFromEvent` then locks the intent row (lock 7), reads the intent's erasure marks, marks the invitation accepted (lock 8), and writes the index rows, the roster version, the action and the idempotency record. A delete takes no erasure gate: it claims the gate row, deletes the index row, advances the roster version, then locks an open delete intent it completes. So an ordinary create or update takes lock 1 before lock 4, as an action does, but a create or update on a transfer intent's record takes the transfer's gate rows before lock 1. That cannot block an erasure, which takes no gate row. The one cycle it allows is an action holding a shared gate and waiting on the event's gate row while an erasure waits on that action's shared gate and the event's shared request queues behind the erasure's exclusive one; the event's edge is a lock-queue wait, which the Postgres deadlock check resolves after `deadlock_timeout` by granting the event's shared request ahead of the waiting erasure, so no transaction fails. A firehose copy that arrives while a local action holds the gate row waits, then finds the rev already stamped.

### Intents and reconciliation

`community_write_intents` (migration 084) holds one row per write in flight: action, actor, admin-acting flag, community, subject, target record URI, operation, the record body for a create or rewrite, the CID of the record a delete replaces, the guard head commit CID and rev, the idempotency key, request fingerprint and idempotency retention, state (`open`, `completed`, `failed`, `expired`), the completing commit rev, record CID and action ID, and the expiry (10 minutes after creation in production). Migration 085 adds an accept's columns: the invitation it settles, the audit actor (the inviter, whom the action names while `actor_did` stays the requesting invitee), and a transfer's paired write (the previous owner's record URI, its moderator body and the CID it replaces, with the URI and body both set or both null). At most one intent per record is open, as a target or as a paired target (`community_write_intents_open_target` and `community_write_intents_open_paired_target`); a record that is one intent's target and another's paired target is caught by the step 6 read, which matches either column. The rows have no foreign key; deleting a community deletes them.

A post action's intent targets the post's removal record and pairs it with the acceptance (migration 088 allows a paired target with no paired record, a paired delete): a remove creates or updates the removal (its body in `record`, the standing removal's CID in `replaced_cid`) and deletes the acceptance (its CID in `paired_replaced_cid`); a restore deletes the removal and writes the acceptance (its body in `paired_record`). Each batch the writer sends is recorded first in `community_write_intent_attempts` (step 11 of § Post remove and restore); the table is insert-only with no foreign key, and the community delete removes its rows.

An open intent is reconciled by a same-key retry or by the sweep, which `cmd/server` runs every 2 minutes on the intents past their expiry, oldest expiry first, each in its own action transaction with the locks above. One pass settles at most 100 intents and reads further pages past the ones it could not settle, so intents awaiting their firehose copy do not hold back newer expired ones. Both read the repo head, then the target records:

- Head still at the guard commit: nothing committed. An unexpired retry re-sends the same writes under the same guard; an accept's retry first rechecks, under the invitee's ban-subject lock, what the accept checked before its intent was stored (`recheckAcceptance`: the invitation open and not lapsed, the invitee not banned, the roster rules), and a refusal marks the intent `failed`. The sweep, or a retry after the expiry, marks the intent `expired`; such a retry then starts over with a fresh intent. Another key's request is refused with `StateConflict` while the intent is unexpired, since its write may still commit.
- Head moved, create or update (`committedWrite`): the write is ours when its target record holds the intent's body (compared as canonical JSON with sorted keys), and for a transfer also when the paired record holds its body, since one commit wrote both. A record that encodes to nothing comparable is `ModerationUnavailable` and leaves the intent open. The intent completes (`completeWrite`) with the head rev, and each record the intent wrote has its gate advanced to the guard rev and its row indexed from the intent's body at that body's CID (the CID read, or for a record changed again since, the CID the PDS assigns the body), unless its gate already holds a later change, which is kept. The write's delayed firehose copies then change nothing, and a later rewrite is indexed by the firehose as an external change. The roster version advances once, one `grant-role` or `transfer-ownership` action names the inviter, and the invitation is accepted. When every record is as it was before the write (absent for a create, at the replaced CID for an update) the write did not happen: the intent is marked `failed` and a retry gets `StateConflict`. Any other state (every record changed to something other than the intent's body) does not show whether the write committed: the intent stays open, the retry or sweep gets `ModerationUnavailable`, the in-flight guards above still apply, and the write's firehose copy completes it.
- Head moved, delete, and the replaced CID is gone (record absent, or present with another CID): the write is ours. The intent completes with the head rev read before the record read, the index row is dropped if it still has the replaced CID, the roster version advances once and one action names the actor. Reconciliation advances the rev gate to the intent's guard rev, not to the head rev it read: a delayed event from at or before the guard can no longer restore the role, the firehose copy of the real commit then finds no row to change, and a later re-grant at a higher rev is indexed with its own action. If the row was already gone (removed by an event that matched no intent, such as an empty-rev delete), that removal logged its action and advanced the version, so the intent completes with that `remove-role` action and adds neither.
- Head moved, delete, and the record still has the replaced CID: the write did not happen. The intent is marked `failed`, nothing is enforced and no action is written; the retry gets `StateConflict`.

A ban or unban intent targets the ban record (`target_uri` the record's AT-URI, `subject_did` the banned account) with no paired target: action `remove` with op `create` or `update` and the record body, or `restore` with op `delete` and the standing record's CID in `replaced_cid`. It records no attempts and is settled by the rules above, reading the ban record instead of a role record. An unexpired retry with the head at the guard re-sends the same write with no recheck: while the ban intent is open, an accept of the subject's invitations is refused. Its completion is `completeBanIntent` (§ Account ban and unban): a `remove` or `restore` naming the actor, the subject's version advanced once when the index changed.

A post intent is settled from its latest recorded attempt and its stand record (the removal for a remove, the acceptance for a restore) instead (`reconcilePostIntent`). The guard is the attempt's guard head, or the intent's when no attempt was recorded; while the head is at it, the rules above apply. Once the head has moved: when the stand record holds the attempt's body under a CID other than the one the attempt recorded before the batch, the commit is ours, and the intent completes with its actor at the attempt's guard rev (the commit's rev is unknown; the gate takes the guard rev so the firehose still applies any later change). When no attempt was recorded, or the stand record is as the attempt found it, the write did not happen: the intent is `failed` and a retry gets `StateConflict`. Otherwise the record changed again after the write (another writer, such as the acceptance engine, the instance-removal outbox or an author edit repinning the acceptance, wrote the same key with a different body); the intent stays open, the retry gets `ModerationUnavailable`, and the firehose copy completes it. If no copy has matched 30 minutes past the intent's expiry (`postIntentFirehoseLag`), the retry, another key's request or the sweep that reaches it marks it `failed` and logs an error, the retry gets `StateConflict`, and the post is no longer blocked; a copy arriving later is an external change, logged without an actor. An intent whose write never committed expires with no admission change and no action.

### Firehose convergence

The role consumer applies each role commit in one transaction (`CommunityRoleRepository.ApplyRoleRecordEvent`): it claims the record's rev gate first, and an equal or older rev writes nothing. A delete that removes an indexed row whose CID is the replaced CID of an open delete intent on the same record, at a rev past the intent's guard rev, completes that intent in the same transaction: the commit rev, one action naming the intent's actor and admin-acting mark (origin `local`), and the idempotency record, so the lost-response retry replays that result. A delete never matches a create or update intent. A create or update completes the open accept or transfer intent that writes the record (as its target or as a transfer's paired target) only when its rev is past the intent's guard rev and its CID is the CID of the intent's body for that record (DAG-CBOR, CIDv1, sha256: what the PDS assigns). The completion indexes every record of the intent from its body in that one transaction, the event's record at the event's CID and a transfer's other record at its body's CID, stamps both gates at the event's rev (both records were in that one commit), advances the roster version once, logs one `grant-role` or `transfer-ownership` action naming the inviter, accepts the invitation and saves the invitee's idempotency record. A transfer's other record keeps a later change already indexed (its gate holds a newer rev): it is neither overwritten nor restored. The transfer's second copy is then stale at its gate and changes nothing, so either delivery order leaves exactly one owner after the first copy. A create or update that does not match (another body, or a rev at or before the guard), and a malformed one that clears the row, is an external change and leaves the intent for the retry or the sweep. Any other role change that alters the index, in any indexed community whether or not it is hosted, writes one action with no actor (origin `inherited`): `grant-role` for a create or rewrite, `remove-role` for a delete or a clearing invalid record. A replay, a stale event, a delete of a row already gone and an identical rewrite write no action and advance no version.

The post consumer indexes community removal records against `community_post_removal_records` (migration 088), keyed by (community, post), which holds the removal record a community holds for a post (key, CID, code, reason, rev) apart from the admission row: an acceptance never clears it, only the removal record's delete. A removal record's create or update (`ApplyRemovalRecord`), in one transaction under the gate rows of the post's removal and acceptance records:

- the index already holds this record (the same CID, code and reason; or, for a removal this AppView stamped without knowing its CID, the same rev): a copy of a change already logged. The CID is filled in, and when the admission does not hold the removal yet (a completion recovered at its guard rev was refused as older than the commit's acceptance delete, already indexed) the removal applies at the event's watermark with no new action, advancing the version only if the decision changed and the commit's acceptance delete did not already advance it;
- an open remove intent of this instance wrote it (the CID of the body its latest recorded batch sent, else of the intent's body, is the event's, and its guard rev is before the event's): the intent completes with its actor at the event's rev, as its local completion would. When the commit's acceptance delete was indexed first and advanced the version, the completion does not advance it again;
- otherwise the removal applies under the watermark rule, advancing the post's version, the record is indexed, and one `remove` action with no actor is logged (origin `inherited`, reason mapped from the code), in any indexed community, hosted or not, including records written outside Coves and by other hosts. No action is logged when the instance removal outbox wrote the record (the record its row owns by CID, or, while one of its writes may still be landing, a record with exactly that write's subject CID, code and `createdAt` and no reason): that removal's instance action is its audit.

A removal record's delete (`ApplyRemovalRecordDelete`) finds its post and code in `community_post_removal_records` by the record's key, else in a row with no key whose post's subject key is the record's. With no row, the index already holds the delete (a local restore dropped the row, or the outbox's restore stamp released it): a post accepted under the key takes the watermark and nothing else changes. An indexed row at a rev not before the delete's makes it stale. Otherwise the withdrawal applies under the watermark rule, advancing the version when it applies, the row is dropped, and one `restore` action with no actor is logged with the deleted removal's mapped code, unless the outbox's restore committed this delete (its row's restore stamp is at the delete's rev). A replay, a stale event and a copy of a change already indexed write no action and advance no version. A delete alone does not show whose commit it is, so it never completes a restore intent: when an open restore intent on the record sent a batch (a recorded attempt) before the delete's rev, the inherited action is marked as awaiting it (the intent's `action_id`). A restore intent completes from its commit's acceptance: an acceptance create (`ApplyAcceptance` with the event's record CID) whose CID is the CID of the acceptance body the intent's latest batch sent, at a rev past its guard rev, completes it with its actor at that rev; an awaiting action is attributed to the actor instead of a second action being logged, and a version the commit's removal delete already advanced is not advanced again. A same-key retry or the sweep that finds the restore committed attributes an awaiting action the same way. A delete with no such acceptance stays an inherited withdrawal: the post returns to pending with no acceptance. A post intent's completion indexes or drops the removal record's identity only over one indexed at a rev not after its gate rev, so a delayed completion keeps a newer record's.

The AppView's own removal writers suppress their echoes the same way. The acceptance engine and the outbox stamp their removal with `ApplyRemoval`, which indexes the record under the subject's canonical key at the stamped rev with no CID, so the firehose copy is recognised by its rev and only fills the CID in. The outbox's restore stamp releases the indexed removal record older than its rev (`ReleaseRemovalRecord`), so the firehose delete finds the index already holding it. A delayed acceptance copy of a restore recovered at its guard rev takes the watermark without advancing the version.

The ban consumer (`handleCommunityBanEvent`, then `CommunityBanRepository.ApplyBanRecordEvent`) accepts a ban record only from an indexed community's repo and only at the key derived from its subject. It applies each commit in one transaction: it claims the record's rev gate first (an equal or older rev writes nothing; an empty rev skips the gate), then the index change, the ban history, the version and the action. A create or update whose CID is the CID of the body of the open ban intent on the record, for the same subject, at a rev past the intent's guard rev, completes that intent with its actor, as its local completion would. A delete completes the open unban intent on the record when its rev is past the intent's guard rev and the indexed row's CID is the CID the intent replaces; an older delayed delete does not. Any other change of the index, in any indexed community, hosted or not, including records written outside Coves, logs one action with no actor (origin `inherited`, migration 090 allows it): `remove` with the record's expiry for a create or rewrite, `restore` for a delete, reversing the subject's latest ban action when that is a `remove`. A ban already indexed as the event has it, and a delete of a ban no longer indexed, log nothing and advance no version. The same-rev copy of a local ban or unban finds the gate already stamped and changes nothing.

Migration 088 back-filled one row with no key, CID or rev for every admission that was `removed`. The pre-read check (step 9 of § Post remove and restore) accepts whatever removal the repo holds for such a row, and a delete of that removal resolves it by recomputing the subject key from the post URI.

Action vocabulary added for roles: `grant-role` (an accepted moderator invitation, or a firehose create or rewrite), `remove-role` and `transfer-ownership` (an accepted ownership offer). Role actions are scoped and authored by the community (`authority_did` = `scope_community_did` = community, `scope_kind = community`), with `subject_uri = at://<subject DID>` and `subject_kind = account`. Their `created_at` is `clock_timestamp()` read when the action is inserted, by both the local and the firehose writers. Each writer holds the record's rev-gate row by then, so one record's changes log in commit order, including a local action that waited on a lock while a firehose change to the record committed. An empty-rev firehose event skips the gate and is not ordered this way.

## Reports and the community queue

Any signed-in account files a report with `social.coves.admin.submitReport` (`admin_reports`, migration 028). Instance admins see every report. The owner and moderators of a hosted community also see the reports on that community's posts and comments, as a queue per community.

- **What is in a community's queue.** Only open reports appear. Reports with the reason `csam` or `illegal` never appear and stay with the instance admins. The other reasons are `spam`, `harassment`, `doxing` and `other`. A report's community comes from the indexed content: `posts.community_did` for a post, and for a comment the community of the indexed post its parent chain reaches (`commentChainCommunitySQL`). It never comes from the reported URI's authority or from the report request. A v1 post URI names the community repo it was written to, which need not be the community it is indexed in. A report on content that is not indexed is in no queue, and a community that is not hosted here has no queue. `postgres.communityReportSQL` is the predicate for all of this, and resolution by removal uses it. Listing and dismissal use `postgres.communityVisibleReportSQL`, which also leaves out a subject its author deleted (`deleted_at` set) and a subject the community has removed: a post whose admission in the community is `removed`, or a comment with an active community removal decision. Reports on such a subject stay open and are listed again if the removal is restored.
- **Who may read and act.** The caller must pass `communities.RoleAuthorizer` at the moderator role: the owner, a moderator or an instance admin, in a community hosted here and not removed (`adminreports.CommunityQueueService`). Anyone else gets `Forbidden`, and nothing is read or written.
- **Listing.** `social.coves.community.listReports?community=&limit=&cursor=` is an authenticated query (`internal/api/handlers/adminreport/community_queue.go`, routes `routes.RegisterCommunityReportQueueRoutes`). It returns one `#reportQueueEntry` per reported subject: `subject`, `subjectType` (`post` or `comment`), the subject's current `post` or `comment` view when it hydrates, the distinct `reasons` in ascending order, `reportCount`, `firstReportedAt` and `lastReportedAt`. A post the caller's view cannot show is served with no `post` and a `postState` taken from its `post.get` result: `blocked` (the caller blocked the author), `removed` (removed by the community), `moderated` (an instance removal) or `notFound` (not shown to the caller, such as a post still pending acceptance or by a restricted author). A comment whose author the caller blocked is served with no `comment` and `commentState` `blocked`, the block rule thread reads apply. Any other comment the caller cannot see is served as the placeholder view a thread shows. Entries run newest last report first, with ties broken by subject URI. `limit` is 1-100 (default 50), and the cursor is opaque. Reporters are never named in the queue; only the admin path shows who filed a report.
- **Dismissal.** `social.coves.community.dismissReports` (`community`, `subject`, `idempotencyKey`) dismisses every community-visible open report on the subject in that community: status `dismissed`, `resolved_by` the caller, `resolved_at` now. It returns `dismissedCount`, which is 0 when nothing was open. Reports filed later reopen the entry.
  - Each dismissal is recorded in `community_report_dismissals` (migration 092), one row per (moderator, community, key). The row is claimed first, in the dismissal's transaction, after the moderator's shared erasure gate.
  - A replay of the key for the same subject returns the stored count and changes nothing, including reports filed since.
  - The same key for a different subject is 409 `IdempotencyConflict`.
  - A moderator whose account has been erased is `Forbidden`.
- **Resolution by removal.** A community removal of a post (a `remove` action) or a comment (an `apply-removal` action) marks the subject's community-visible open reports in that community `resolved`. This covers a local completion, the sweep and a firehose removal with or without an intent. It runs in the transaction that logs the action (`insertCommunityPostAction`, `insertCommentRemovalAction`), so a failure rolls back the removal too. `resolved_by` is the action's actor, or NULL for an action with no actor or whose actor's account has been erased. A removal can complete after its actor's erasure (the PDS response was lost, and the sweep or the firehose copy completes it later), so `resolveCommunityReportsTx` takes the actor's shared erasure gate and reads the marker before it writes `resolved_by`. Every path already holds that gate before any index row an erasure locks: a local action and the sweep take it in `lockCommunityAction` (lock 1), and a firehose removal record takes the gates of the open remove intents' actors on the record (`gateRemovalIntentActors`) right after its rev-gate rows, which erasure never takes. `csam` and `illegal` reports stay open, and restores do not reopen reports.
- **Account erasure.** `user_repo.go` `Delete` (step 12a) deletes the reports the account filed and the dismissal records naming it. It also clears the account from `resolved_by` on reports it closed, which keep their status. Report creation takes the reporter's shared erasure gate, so an erased account's report is refused with `ErrReporterErased` (401 `AuthRequired`) and nothing is stored. Deleting a community deletes its dismissal records.

## Published labels

With `LABEL_SIGNING_KEY` set, each instance removal, restore, NSFW label and NSFW retraction writes one signed atProto label (`!takedown`, `!takedown` neg, `nsfw`, `nsfw` neg) in its decision transaction, and `com.atproto.label.queryLabels` serves them. The AppView serves an instance DID document at `/.well-known/did.json` listing the `#atproto_label` key and `#atproto_labeler` endpoint, but production serves the static `static/.well-known/did.json` through Caddy, which lists the same `#atproto_label` key and `#atproto_labeler` endpoint; every key rotation updates `#atproto_label` there in the same deploy. The first boot with a key exports the decisions already active; a key change needs `LABEL_SIGNING_KEY_RETIRING` and re-signs every label at boot. Once a label is stored or that export has completed, a boot without `LABEL_SIGNING_KEY` fails (`ErrSigningKeyRequired`), so decisions are never made unpublished. `com.atproto.label.subscribeLabels` streams the same labels. Details are in [plans/MODERATION_LABELS.md](plans/MODERATION_LABELS.md) § Built today.

## Not built

- Consuming other sources' labels: see [plans/MODERATION_LABELS.md](plans/MODERATION_LABELS.md). Coves publishes its own (§ Published labels); whether Lemmy sees an instance removal of native content depends on Tidepool consuming them, which is outside this repo.
- An acceptance engine removal whose firehose copy arrives before the engine's own stamp is indexed as an external change: it logs a community `remove` action with no actor (origin `inherited`) in addition to the engine's decision.
- Evidence retention for illegal-content removals, which keep no snapshot, and modlog editing.
